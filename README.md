# 软件项目开发 Skill 集合

本目录包含一套完整的**软件项目开发流水线技能**，共 15 个独立 Skill，覆盖从需求分析到发布上线的整个软件工程流程。

每个技能对应一个独立文件夹，包含一个 `SKILL.md`（名称、触发条件 + 使用说明）。

## 编写背景

在软件项目开发中，把会写代码的 AI 直接抛给一句模糊的需求，往往得到的是结构混乱、难以维护、缺乏测试与安全的代码——"拿到需求就写代码"的做法让工程质量不可控。

实际的软件工程有其成熟的方法论：先搞清楚**要做什么**，再设计**用户怎么用、系统怎么实现**，然后才**写代码、做校验、发布上线**。每一步都有明确的目标和产出物，缺一步都会让后续环节付出高昂代价。

为了把这种**规范化、可复现的工程流程**固化下来，我们按软件工程的各个阶段拆分成 15 个独立 Skill，每个 Skill 只专注一个环节，职责单一、边界清晰：

- **总控调度**：用一个 `project-orchestrator` 管理整条流水线，保证"先理解、再设计、后编码、再验证"的顺序不被跳过。
- **按阶段分工**：14 个阶段技能各司其职，前一阶段的产出即后一阶段的输入，保证质量层层把关。
- **可回退纠偏**：后一阶段发现问题时可回退到问题根因所在阶段，避免带病推进。
- **沉淀最佳实践**：把"无数据不做性能优化""修复根因而非表面错误""测试测的是需求而非代码"等工程经验写进每个技能，让 AI 的每次开发都遵循同一套高质量标准。

这套 Skill 集合的目标是：让 AI 按软件工程流程开发，减少重复决策、提升产出一致性，从而获得更可靠、更可维护的软件交付。

## 设计理念

> 让 AI 按照软件工程流程开发，而不是拿到需求后直接开始写代码。

整条流水线由 `project-orchestrator` 作为总控调度，其余 14 个阶段技能按固定顺序协作。每个阶段有明确的**最终目标**与**关键产出物**，前一阶段的产出作为后一阶段的输入，发现问题时支持回退。

## 一、技能清单与作用

| 编号 | Skill 名称 | 文件夹 | 作用（一句话） |
| ---- | ---------- | ------ | ------------- |
| 00 | `project-orchestrator` | `project-orchestrator/` | 管流程：判断阶段、调度技能、检查完成度、决定推进或回退 |
| 01 | `requirements-analysis` | `requirements-analysis/` | 搞清楚**做什么**：把自然语言需求转成明确、可执行的开发需求 |
| 02 | `product-design` | `product-design/` | 搞清楚**用户怎么用**：将需求转成功能模块、页面结构与用户/业务流程 |
| 03 | `architecture-design` | `architecture-design/` | 搞清楚**系统怎么实现**：技术栈、模块划分、部署与扩展方案 |
| 04 | `database-design` | `database-design/` | 搞清楚**数据怎么存**：表结构、字段、索引、关系与约束 |
| 05 | `api-design` | `api-design/` | 搞清楚**前后端怎么通信**：接口契约、错误码与统一约定 |
| 06 | `ui-design` | `ui-design/` | 搞清楚**界面怎么做**：页面、组件、交互与各状态设计 |
| 07 | `development` | `development/` | 把**设计写成代码**：实现业务逻辑、API、数据库与页面 |
| 08 | `code-review` | `code-review/` | 检查**代码有没有问题**：质量、可维护性、边界、并发与潜在 Bug |
| 09 | `testing` | `testing/` | 验证**功能是否正确**：覆盖正常/异常/边界/权限等场景 |
| 10 | `debugging` | `debugging/` | 解决 **Bug**：复现→定位→根因→最小修复→回归 |
| 11 | `security-review` | `security-review/` | 检查**安全问题**：注入、XSS、越权、敏感信息、依赖漏洞等 |
| 12 | `performance-optimization` | `performance-optimization/` | 解决**性能问题**：以数据为准定位瓶颈并优化 |
| 13 | `documentation` | `documentation/` | 把**项目说明白**：README 与各专项文档 |
| 14 | `release` | `release/` | 把**项目发布出去**：构建、部署、验证、发布、监控 |

### 使用要点

- 从 **00 `project-orchestrator`** 入口开始，由它判断并推进整个流程。
- 阶段顺序通常严格固定：**设计先行 → 编码 → 验证 → 收尾**。
- 后一阶段发现问题时，回退到问题根因所在阶段修复后再继续（最小回溯）。
- 各阶段的核心职责速记：

```
project-orchestrator        管流程
requirements-analysis       搞清楚做什么
product-design              搞清楚用户怎么用
architecture-design         搞清楚系统怎么实现
database-design             搞清楚数据怎么存
api-design                  搞清楚前后端怎么通信
ui-design                   搞清楚界面怎么做
development                 把设计写成代码
code-review                 检查代码有没有问题
testing                     验证功能是否正确
debugging                   解决 Bug
security-review             检查安全问题
performance-optimization    解决性能问题
documentation                把项目说明白
release                     把项目发布出去
```

## 三、各技能产出物速查

| 阶段 | 关键产出物 |
| ---- | ---------- |
| requirements-analysis | 需求规格说明（功能/非功能需求、业务规则、验收标准） |
| product-design | 产品方案（功能模块、页面结构、用户/业务流程、状态与异常） |
| architecture-design | 架构设计（技术栈、模块划分、部署与扩展方案） |
| database-design | 数据库设计（表结构、字段、索引、关系、约束） |
| api-design | API 契约（URL、方法、参数、响应、错误码、权限） |
| ui-design | 界面设计（页面、组件、交互、各状态） |
| development | 可运行的代码，编译运行通过 |
| code-review | 审查报告（问题分级，无未处理 Critical/Major） |
| testing | 测试用例 + 执行结果，符合需求 |
| debugging | 根因分析 + 最小修复 + 回归通过 |
| security-review | 安全检查报告（高风险项清零） |
| performance-optimization | 性能分析 + 优化方案/结果 |
| documentation | README 与各专项文档 |
| release | 已构建、已部署、健康检查与冒烟通过 |

## 四、使用方式

按需调用对应技能即可，例如：

- 用户说"开发一个 XX 系统" → 触发 00 `project-orchestrator`，进入完整流水线。
- 已有明确需求，想确认到底做什么 → 触发 01 `requirements-analysis`。
- 代码写好了，想检查质量 → 触发 08 `code-review`。
- 出现线上 Bug → 触发 10 `debugging`。
- 准备上线 → 触发 14 `release`。
