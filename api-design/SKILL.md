# api-design

负责前后端**接口设计**。

## 最终目标

> 前端和后端如何通信。

## 设计内容

对每个接口明确定义：

- **API URL**：路径命名遵循 RESTful 资源语义
- **HTTP Method**：GET / POST / PUT / DELETE / PATCH
- **请求参数**：path / query / header 参数及含义
- **Request Body**：数据结构、必选/可选字段
- **Response**：成功响应的数据结构
- **HTTP Status**：正确使用状态码（200/201/400/401/403/404/409/500 等）
- **错误码**：业务错误码体系，机器可读
- **权限要求**：是否需要认证/授权，允许的角色
- **数据格式**：字段命名风格（camelCase/snake_case）、日期格式、金额精度
- **分页**：页码/游标，page/pageSize 约定
- **排序**：排序字段与方向
- **筛选**：查询条件如何传递
- **参数校验**：必填、类型、范围、格式约束

## 统一性保证

在设计时保证以下一致：

- **API 命名统一**：资源名、路径、动作风格一致
- **数据结构统一**：通用响应包装（如 `{ code, message, data }`）统一
- **错误处理统一**：错误响应结构、错误码格式统一
- **权限规则统一**：认证鉴权机制与角色校验方式一致
- **校验规则统一**：同类字段的校验方式一致

## 设计原则

- **面向资源建模**：动词尽量收敛为资源的 CRUD + 必要的动作型接口。
- **向前兼容**：为扩展留空间（可加字段，避免删改既有字段）。
- **幂等性**：对重复请求安全（PUT/DELETE 语义明确）。

## 输出

ALWAYS 使用以下结构生成 API 设计：

```
# API 设计
## 1. 通用约定（Host、认证、通用响应包装、错误码体系、分页/日期/金额格式）
## 2. 权限模型（角色 → 可访问接口/接口粒度权限）
## 3. 接口清单总览
## 4. 接口定义（每个：Method/URL、参数、Request、Response、Status、错误码、权限、示例）
## 5. 统一错误码表
## 6. 一致性检查（命名/结构/错误/权限/校验）
## 7. 待确认问题
```

## 接口定义模板

对每个接口使用一致模板：

```
### POST /api/{resource}
- 描述
- 权限：...
- 请求参数 / Request Body（含校验）
- Response（成功 / 失败示例）
- HTTP Status 与错误码
```

## 常识

- 接口是前后端契约，一旦联调后变更成本高：设计阶段就把契约钉死。
- 统一的响应包装与错误码，能显著降低调用方的对接与排错成本。
