# api-design

负责前后端**接口设计**。

## 最终目标

> 前端和后端如何通信：契约清晰、统一、可追溯，联调前把边界钉死。

## 〇、执行边界与指令优先级

> **用户显式指令优先于本技能指南。** 用户要求与以下冲突时，按用户要求执行并说明差异。

- **输入**：database 的字段映射、product/ui 的数据需求、architecture 的边界。
- **步骤**：统一约定 → 逐接口契约 → 幂等/版本 → 错误码 → 追溯 → OpenAPI 产出。
- **输出**：可做前后端契约的接口定义（方法/路径/Schema/错误码/权限 + OpenAPI）。
- **不可臆测**：接口字段必须源于数据/业务需要，不发明字段；与 database/product 可追溯。
- **何时询问/停止**：字段语义或权限边界不清时先确认。
- **支持文件**：完整契约示例见 `references/example-contract.md`（需要产出/对照完整契约时加载）；其余 OpenAPI 模板可放 references/ 或 assets/，从本文件引用并注明何时加载。

## 一、强制输出（不可省略）

1. **统一约定**：路径风格、鉴权方式、分页、排序、过滤、错误体。
2. **每个接口**写清：方法、路径、请求/响应 Schema、错误码、权限。
3. **幂等与重试语义**（尤其写操作）。
4. **版本策略**（URL / Header）及兼容原则。
5. **追溯**：接口 ↔ database / product（对应功能与数据）。

## 二、输入与前置

- 输入：product-design（功能/流程/权限矩阵）、database-design（业务对象与字段映射）。
- 接口面向产品功能与业务对象设计，字段命名与语义与数据库/业务对象对齐。

## 三、统一约定（强制）

### 路径风格
- RESTful：资源用复数名词 `/api/{resources}/{id}`，动词收敛为 CRUD + 必要动作型 `/api/{resource}/{id}/actions`。

### 鉴权方式
- 统一一种主鉴权（如 Bearer Token / JWT + 刷新），说明携带位置（Authorization 头）与过期处理。
- 明确无需鉴权的接口豁免清单。

### 分页
- 约定一：页码式 `page` + `pageSize`（默认/上限，如 1/20/100）。
- 或游标式 `cursor` + `limit`（适合流式/高频更新）。
- 响应统一返回 `{ items, page, pageSize, total }` 或 `{ items, nextCursor }`。

### 排序
- 统一参数：`sort=field`、`order=asc|desc`（或 `sort=+field,-field`）。
- 排序白名单：仅允许排序的字段列表，防注入与乱排序。

### 过滤
- 统一传参方式（query 参数或 filter 对象），同一字段类型与格式。
- 范围/多值过滤有统一表示（如 `status=1,2`、`created_from=...`）。

### 错误体（统一结构）
```
{ "code": "TASK_NOT_FOUND", "message": "任务不存在", "details": {...} }
```
- `code`：业务错误码（机器可读）；`message`：人可读；`details`：可选字段级信息。

## 四、单个接口定义模板（强制字段）

每个接口使用一致模板，字段全部写清：

```
### POST /api/tasks
- 权限：登录用户（可创建任务）；管理员可建任意用户任务
- 请求 Schema：{ title: string(必填, ≤200), due_date: date?(可空) }
- 响应 Schema：201 → Task 对象；422 → 校验错误体
- 错误码与 HTTP：
  借 201 创建成功；400 参数格式错误；401 未认证；422 业务校验 `TITLE_EMPTY`
- 幂等：不支持幂等（POST 创建每次新建）；重试需谨慎，见幂等节
```

强制项：**Method / 路径 / 请求 Schema / 响应 Schema / 错误码 / 权限**，缺一不可。

## 五、幂等与重试语义（尤其写操作）

- **GET / DELETE / PUT**：天然/可设计为幂等，重复执行结果一致。
- **POST（创建）**：默认非幂等，需处理重复提交：
  - 提供 `Idempotency-Key`（调用方生成，服务端去重返回首次结果）。
  - 或改 POST 为支持客户端生成 ID（`PUT /api/tasks/{clientId}`）实现幂等创建。
- **重试**：对网络超时可安全重试的接口（幂等或带 Idempotency-Key）才允许重试 1~N 次；非幂等写操作不得盲目重试。
- 明确"哪些操作可重试、间隔与上限"。

## 六、版本策略与兼容原则

- **方式**：URL 版本 `/api/v1/...` 或 Header 版本 `Accept: application/vnd.app.v1+json`。
- 优先 URL 版（简单、显式、易缓存与路由）。
- **兼容原则**：
  - 兼容 = 只增不改不删：可加可选字段/新枚举，不删改既有字段语义。
  - 破坏性变更必须升版本，旧版本保留至弃用期（给出弃用窗口）。
  - 新版本发布时明确废弃与迁移路径。

## 七、追溯接口 ↔ database / product

- 每个接口标注：**对应产品功能**（关联产品功能/需求编号）与**主要数据来源**（表/业务对象）。
- 反向也要可查：某功能/数据被哪些接口覆盖，避免遗漏或重复。

```
POST /api/tasks → 功能：创建任务 FR-2；数据：tasks 表（title, user_id, status, due_date）
```

## 八、建议增强

### 错误码分层（业务码 vs HTTP 状态）示例表
- 两层：**HTTP 状态**（传输层语义，如 401/403/404）与**业务码**（业务语义，`TASK_NOT_FOUND`）。
- 示例表：
| HTTP | 业务码 | 含义 | 触发 |
| 400 | BAD_REQUEST | 请求格式错误 | 参数类型错 |
| 401 | UNAUTHORIZED | 未认证 | 无/过期 Token |
| 403 | FORBIDDEN | 无权限 | 越权操作 |
| 404 | NOT_FOUND | 资源不存在 | id 无效 |
| 409 | CONFLICT | 冲突 | 重复/状态冲突 |
| 422 | VALIDATION_ERROR | 校验失败 | 字段不合法 |
| 429 | RATE_LIMITED | 限流 | 超频 |
| 500 | INTERNAL | 服务内部错 | 异常 |

### 限流、超时、批量接口约定
- **限流**：说明限流维度（用户/IP）、额度与返回的 `Retry-After`、429 错误体。
- **超时**：约定客户端与网关超时时间；长任务用异步 + 轮询/回调，不用长同步。
- **批量**：批量接口约定上限（如一次 ≤ 100）、部分失败语义（整批回滚 or 逐条返回结果）。

### OpenAPI / 等价契约
- 若技术栈支持，产出 OpenAPI（`openapi: 3.x`）作为唯一契约来源，接口由契约驱动（可复用生成客户端）。
- 契约与文档保持一致，作为联调与测试依据。

### 内部 API vs 公开 API
- **公开 API**：需要更严格版本控制、限流、鉴权、合规与文档。
- **内部 API**：可共享内网鉴权、更少对外约束，但同样保持契约与错误统一。
- 明确哪些是公开、哪些是内部，避免内部接口被误当公开接口滥用。

## 十、质量门槛

### 完成判定（全部满足才可进入下一阶段）

- [ ] **核心读写接口齐全**：产品要求的主要读写路径都能被接口覆盖
- [ ] 统一约定完整（路径/鉴权/分页/排序/过滤/错误体）
- [ ] 每个接口含 Method/路径/请求·响应 Schema/错误码/权限
- [ ] 写操作明确了**幂等与重试语义**
- [ ] 说明了**版本策略与兼容原则**
- [ ] **错误与权限有定义**（全接口覆盖，无未定义错误）
- [ ] 无模糊的"等"字段——每个字段类型与约束明确
- [ ] 能追溯到 database / product

### 不合格信号

- 接口只有路径与一句话，缺请求/响应 Schema
- 错误码缺失或不统一
- 权限未定义或含糊
- 写操作无幂等考虑
- 出现"其他字段等""参数等"等模糊表述
- 无版本策略，破坏性变更无纪律

## 十一、完整接口契约示例

- 需要一份"合格完整契约长什么样"时，加载 `references/example-contract.md`（完整示例，含错误响应与追溯）。
- 示例仅作对照用途；实际编写接口，仍需按本 SKILL.md 的模板与规则逐项补齐，不得照抄示例字段。

## 常识

- 接口是前后端契约，联调后变更成本高：设计阶段把契约钉死。
- 统一响应包装、错误码与幂等语义，能显著降低调用方对接与排错成本。
- 没有"等"字段：每个字段的类型与约束都应是确定的。
