# architecture-design

负责系统**技术架构**设计。

## 最终目标

> 系统应该怎么实现：技术栈、模块、部署与工程实践被明确到可落地、可 review 的程度。

## 一、强制输出（不可省略）

1. **总体架构图**：分层/模块/服务及其关系（Mermaid 或图）。
2. **目录结构**：工程目录与分层（如 Controller/Service/Repository）。
3. **模块边界与依赖方向**：每模块职责 + 依赖方向，标注禁止反向/循环依赖。
4. **部署拓扑与环境划分**：明确 dev / staging / prod 及其差异。
5. **可观测性设计**：日志、指标、链路追踪的最小方案。
6. **配置与密钥管理原则**：禁止硬编码、环境隔离。
7. **技术选型的理由与取舍**（为何选 / 为何不选，单一成节）。
8. **风险与假设**（单独成节，供 review）。

## 二、输入与前置

- 输入：requirements-analysis、product-design 的产出。
- 从产品方案（功能模块、权限矩阵、非功能指标）推导架构需求。
- 若产品阶段有未关闭问题，先回退，不擅自假设。

## 三、架构风格选型（多仓 / 单体 / 模块化单体）

根据规模与团队给出选择：

| 形态 | 适用 | 取舍 |
| ---- | ---- | ---- |
| **单体 (Monolith)** | 小团队、早期、MVP | 简单、成本低；扩展与隔离较弱 |
| **模块化单体** | 中等规模 | 内部强边界、可演进到拆分；部署仍一体 |
| **微服务** | 大规模、多团队、独立扩缩 | 独立部署/扩展；运维与分布式复杂度高 |

指引：
- 默认从**模块化单体**起步，非必要不直接上微服务。
- 只有出现明确信号（独立扩缩、多团队边界、部门隔离）再考虑拆分。
- 写清"为什么选这个形态、为什么暂不选其他"。

## 四、技术选型：必须写理由与取舍

对每项选型给出结构化理由：

```
## 技术选型
### 后端：Java 21 + Spring Boot 3
- 为何选：团队熟悉；生态成熟；类型安全利于长久维护。
- 为何不选（弃选）：
  - Node.js/Express：近实时场景少、类型约束弱。
  - Go：并发强但团队不熟、业务 CRUD 生态略弱。
- 取舍：偏工程化、启动略重；换取类型安全与维护性。
```

- **为何选**：正面理由。
- **为何不选**：至少列出被弃选的候选及其否因。
- **取舍**：选型付出的代价与换取的收益。

## 五、总体架构图

用 Mermaid 绘制总体结构，标注模块/服务与依赖方向。

示例：
```
graph TD
    Client[Web/移动端] --> GW[网关]
    GW --> Auth[认证服务]
    GW --> Core[任务服务]
    Core --> Cache[(Redis)]
    Core --> DB[(PostgreSQL)]
    Core --> MQ[消息队列]
    MQ --> Notify[通知服务]
```

- 箭头即依赖方向，写明"依赖只允许单向"。

## 六、目录结构与模块边界

给出工程目录，并定义模块职责与依赖方向。

```
├── module-core/          # 领域模型与业务规则
├── module-api/           # 对外接口/契约
└── module-app/           # 应用编排(Controller/Service)
```

### 模块边界（示例）
| 模块 | 职责 | 依赖 | 禁止依赖 |
| ---- | ---- | ---- | -------- |
| module-core | 领域对象、状态机 | 无 | 外部模块 |
| module-api | DTO/契约 | core | 实现细节 |
| module-app | 用例编排 | core, api | 反向依赖core-impl |

- **无职责重叠**：每个模块单一职责，不重复承担责任。
- **依赖单向**：只允许往下/向外，禁止循环依赖。

## 七、部署拓扑与环境划分

明确环境划分与差异：

```
| 环境 | 用途 | 部署形态 | 数据库 | 备注 |
| dev  | 开发 | 本地/单机 | 本地库 | 可重置 |
| staging | 预发布 | 复用 prod 形态 | 独立库 | 与 prod 隔离 |
| prod | 生产 | 容器/集群 | 独立库 | 有备份/监控 |
```

- 各环境**独立资源与配置**，staging 不再使用 dev 数据。
- 拓扑包含：接入层（网关/负载均衡）、应用层、数据层、中间件。

## 八、可观测性设计（日志、指标、链路追踪——最小方案）

### 日志
- 分级（DEBUG/INFO/WARN/ERROR），结构化（JSON）便于检索。
- 关键业务节点打 INFO，异常打 WARN/ERROR，带上下文 ID。
- **脱敏**：不记录密码、Token、敏感字段。

### 指标
- 核心指标：接口 QPS、P95/P99 延迟、错误率、CPU/内存、DB 连接、队列积压。
- 采用标准采集（如 Prometheus 暴露 /metrics）。

### 链路追踪
- 引入 traceId：请求进入时生成，贯穿日志与跨服务调用。
- 日志统一输出 traceId，便于串联排查。

```
最小可观测栈：结构化日志(含traceId) + 指标端点( /metrics ) + 可选 tracing 库。
```

## 九、配置与密钥管理原则

- **禁止硬编码**：数据库地址、密钥、Token、第三方凭据一律不进代码/仓库。
- **环境隔离**：dev / staging / prod 使用各自配置来源，运行时注入。
- **密钥管理**：使用环境变量或密钥管理服务（如 Vault / 云 KMS），不在仓库明文存储。
- 每个环境一份配置，明文默认值可进仓库，敏感项必须外部注入。

## 十、CI/CD 与发布策略（原则性说明）

- 说明 CI 触发（push/PR）、校验（lint/测试/构建/扫描）、产物（镜像/版本）。
- 发布策略原则：小步、可回滚；优先蓝绿或滚动（按规模选）。
- 明确各环境的发布通道与人工/自动审批边界。
- 详细实现放 release 阶段，此处仅给原则与边界。

## 十一、扩展性边界：当前不做但预留

- 明确"当前不做"的扩展点，但说明预留边界与将来接入方式。
- 避免为想象中的需求过度设计，只预留真实信号支持的边界。

```
预留：消息队列未来用于通知，当前先保证领域层事件可发；待需求明确再接入 MQ。
```

## 十二、风险与假设（单独成节）

- **风险**：技术栈无人熟悉、依赖外部服务不稳定、数据规模超预期等。
- **假设**：技术选型与削设计所依据的当前事实与前提（数据规模、团队、预算）。
- 风险需给缓解措施；假设需在 review 时被重新核对。

## 十三、输出

ALWAYS 使用以下结构生成架构设计：

```
# 系统架构设计
## 1. 架构风格与形态选型（多仓/单体/模块化单体，含取舍）
## 2. 总体架构图（Mermaid）
## 3. 技术栈选型（每项：为何选/为何不选/取舍）
## 4. 项目目录结构
## 5. 模块划分与职责、依赖方向（无重叠、无循环）
## 6. 部署拓扑与环境划分（dev/staging/prod）
## 7. 可观测性设计（日志/指标/链路追踪）
## 8. 配置与密钥管理
## 9. 第三方依赖与中间件
## 10. CI/CD 与发布策略（原则）
## 11. 扩展性边界（当前不做但预留）
## 12. 风险与假设
## 13. ADR 记录（可选，见下）
```

## 十四、ADR（架构决策记录）模板（可选但推荐）

对重大技术决策用 ADR 固化，便于追溯：
```
# ADR-001: 采用模块化单体而非微服务
状态：已接受
背景：团队 < N 人，MVP 阶段，无独立扩缩需求。
决策：采用模块化单体，内部保持强边界。
后果：部署简单、演进留口；拆分时机由"边界信号"触发。
备选：微服务（运维复杂度高，暂不合适）。
```

## 十五、质量门槛

### 完成判定（全部满足才能进入下一阶段）

- [ ] 技术栈每项都有**理由与取舍**（为何选/为何不选）
- [ ] 模块**职责无重叠**、依赖方向明确、无循环依赖
- [ ] 部署拓扑与环境划分（dev/staging/prod）**可执行**
- [ ] 配置与密钥管理**禁止硬编码**、环境隔离明确
- [ ] 可观测性最小方案（日志/指标/链路追踪）已给出
- [ ] **风险与假设**单独成节
- [ ] 产品方案中被明确要求的非功能指标可在本架构承载

### 不合格信号

- 技术选型只列名称、无理由无取舍
- 模块职责重叠或依赖混乱
- 未明确环境划分或配置/密钥有硬编码倾向
- 无可观测性设计
- 无风险与假设
- 架构与产品/非功能需求脱节

## 十六、合格架构文档示例（精简）

```
# 系统架构设计（示例：任务管理 Web 应用）

## 1. 形态选型
模块化单体：小团队、MVP，无需独立扩缩；内部强边界，保留演进为微服务的可能。

## 2. 总体架构图
graph TD
    Client --> GW[网关]
    GW --> Core[任务应用]
    Core --> Cache[(Redis)]
    Core --> DB[(PostgreSQL)]

## 3. 技术栈选型
- 后端 Java 21 + Spring Boot 3
  为何选：团队熟、生态成熟、类型安全。
  为何不选：Node/Express(类型弱)、Go(团队不熟)。
  取舍：启动略重，换类型安全与维护性。
- 前端 React 18 + TS：生态与类型安全；弃用 Vue(团队偏好差距小)。
- 数据库 PostgreSQL 15：事务完整、扩展性好；弃用 MySQL(团队更熟 PG 特性)。

## 4. 目录结构
├── module-core/   # 领域模型与状态机
├── module-api/    # DTO/契约
└── module-app/    # 用例编排

## 5. 模块职责与依赖（表格：模块/职责/依赖/禁止依赖）

## 6. 部署拓扑与环境划分
| 环境 | 形态 | 数据库 | 密钥 |
| dev  | 单机 | 本地库 | 本地 env |
| staging | 容器 | 独立库 | 测试密钥服务 |
| prod | 集群 | 独立库 | KMS/Vault |

## 7. 可观测性
结构化日志(JSON+TraceId)、/metrics 指标(P95延迟、QPS、错误率)、链路追踪贯穿请求。

## 8. 配置与密钥
禁止硬编码；各环境独立配置；密钥走环境变量/KMS，不入仓库。

## 12. 风险与假设
风险：外部认证服务不稳 → 加超时与降级。
假设：并发 ≤ 500、数据规模 < 100 万，后续 review 复核。
```

## 常识

- 架构是技术方案的骨架，方向错误会在开发阶段付出高昂代价。
- 优先推荐成熟、团队熟悉的技术，而非追新。
- 选型必须可辩护：能讲清为何选、为何不选、代价是什么。
