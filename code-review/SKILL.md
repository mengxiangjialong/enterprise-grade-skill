# code-review

负责**代码审查**。

## 最终目标

> 判定当前代码是否达到进入测试阶段的条件，并输出可执行的修复依据。

## 〇、执行边界与指令优先级

> **用户显式指令优先于本技能指南。** 用户要求与以下冲突时，按用户要求执行并说明差异。

- **输入**：development 交付的代码 + 交接清单、需求/各设计产出。
- **步骤**：对照需求设计 → 逐维度走查 → 重点风险区深入 → 分级记录 → 汇总结论。
- **输出**：含位置/问题/影响/建议修复的审查报告 + 明确结论（是否可进 testing）。
- **不可臆测**：结论必须有证据与位置，不拍脑袋评级；Critical/Major 未清零强制回退。
- **何时停止**：Critical/Major 未清零时判定不通过并回退 development。
- **支持文件**：检查清单可放 references/，从 SKILL.md 引用并注明何时走查。

## 一、审查必须对照需求与设计（强制）

- 审查不只挑代码风格，而要**对照需求规格与各设计**（产品/架构/DB/API/UI）核对实现是否符合：功能行为、接口契约、字段、目录分层、模块边界。
- 目标：发现"实现了却没做对需求"和"做了需求外的多余改动"，两者都算问题。
- 读相关需求/设计片段作为依据，而非仅凭代码自洽。

## 二、检查维度 + 每类常见问题示例

逐维度走查，每类给出常见问题示例以提示：

- **功能正确性**（实现是否符合需求/设计）
  例：查列表返回了别人数据（越权）、状态机少一条转移、金额精度丢失。
- **代码质量**（结构/命名/职责）
  例：God Class 一个类做所有事、命名语义模糊、重复逻辑散落。
- **可读性**（他人能否快速理解）
  例：长方法、魔法数字、缺少必要边界注释。
- **可维护性**
  例：硬编码配置、耦合过深、改动影响面大。
- **重复代码**
  例：同逻辑复制 3 处，未抽公共方法。
- **类型安全**
  例：`any`/`Object` 滥用、隐式字符串转数字、强转导致运行时错。
- **异常处理**
  例：catch 吞异常不日志、裸捕获 `Exception`、错误只返回 `false` 无上下文。
- **边界条件**
  例：未处理空集合/空值、除零、极端输入、索引越界、`0`/`null` 未区分。
- **资源释放**
  例：连接/流/锁未 `finally` 关闭、异常路径泄漏、超时未设置。
- **并发问题**
  例：共享可变状态无锁、check-then-act 竞态、集合遍历中修改、懒加载线程安全。
- **数据库问题**
  例：N+1、关联查询无索引、事务范围过大、锁粒度过大。
- **潜在 Bug**
  例：比较问题（引用 vs 值）、边界条件翻转、错误分支逻辑。

## 三、重点风险区清单（深入审查）

以下区域必须**逐一深入审查**，参见二节示例：

- **鉴权 / 越权**：接口是否有鉴权、水平/垂直越权、IDOR
- **金额 / 数值**：精度、单位、舍入、溢出、负数校验
- **并发**：竞态、死锁、共享状态、原子性
- **SQL / 数据访问**：注入、N+1、无索引、事务边界、隔离级别
- **资源释放**：连接、流、线程、锁、缓存占用

## 四、问题分级（写死规则）

```
Critical     会导致故障/数据错误/安全漏洞，必须修复
Major        明显缺陷，影响正确性或稳定性，应修复
Minor        小问题，影响质量但不阻塞，建议修复
Suggestion   可优化项，供参考，不强制
```

### 强制回退规则（写死）

> **只要存在未处理的 Critical 或 Major → 强制回退 development，不得继续进入 testing。**

- 任一 Critical 未清零 → 回退 development
- 任一 Major 未清零 → 回退 development
- 仅剩 Minor / Suggestion → 可进入 testing（Minor/Suggestion 可作为 backlog 继续跟进）

## 五、报告条目必须含四要素（强制）

每条问题 ALWAYS 包含：**位置、问题、影响、建议修复**。

```
- 位置：src/.../TaskService.java:121
- 问题：删除任务未校验归属，其他用户可删任意任务（越权）
- 影响：水平越权，数据被非法删除；HIGH
- 建议修复：在 Service 层校验 task.user_id == currentUser.id，不匹配抛 Forbidden
```

## 六、与静态分析 / linter 结合

- 可运行静态分析 / linter / 类型检查（如 ESLint、Checkstyle、golangci-lint、formatter）作为**辅助**。
- 但**不替代人工维度**：工具抓风格与明显缺陷，人工审查负责需求对齐、鉴权、业务逻辑、架构边界等工具难判的部分。
- 在报告中说明：`工具已跑：<工具名>，剩余项为人工审查发现`。

## 七、保留「亮点」一节（不只看坏消息）

- 主动记录做得好的方面（正确实现的需求、优雅的边界处理、规范命名等），让审查客观、肯定优点，避免只报坏消息。
- 「亮点」有助于后续团队维持好的模式。

## 八、按语言/框架的补充检查点（可选附录）

按技术栈追加专项检查点，例如：
- **Java/Spring**：依赖注入范围、事务注解范围、bean 生命周期、SQL 注入（JDBC 拼接）
- **Node/TS**：异步错误处理、Promise 泄漏、原型污染、事件监听泄漏
- **前端/React**：Hooks 依赖、副作用清理、key、memo 滥用、XSS 渲染
- **Go**：goroutine 泄漏、error 处理、锁复制、slice/map 并发写

（按项目实际技术栈选用，不强制全部。）

## 九、输出

ALWAYS 使用以下结构生成代码审查报告：

```
# 代码审查报告
## 1. 审查范围与目标（含所对照的需求/设计）
## 2. 静态分析/linter 结果（辅助，不替代人工）
## 3. Critical / Major 问题（位置/问题/影响/建议修复）
## 4. Minor 问题
## 5. Suggestions
## 6. 重点风险区专项审查结果（鉴权/金额/并发/SQL/资源）
## 7. 亮点与符合规范的方面
## 8. 结论：是否达到进入测试阶段的条件（明确）
```

## 十、质量门槛

### 完成判定（全部满足）

- [ ] **无未处理 Critical / Major**（有则回退 development）
- [ ] **结论明确**是否可进 testing（不模棱两可）
- [ ] 对照需求与设计审查（非仅风格）
- [ ] 每条问题含**位置/问题/影响/建议修复**
- [ ] 重点风险区均已专项审查
- [ ] 报告含「亮点」，客观完整

### 不合格信号

- 结论含糊，未明确可否进入 testing
- 有 Critical/Major 未处理却判"通过"
- 只看代码风格，未对照需求/设计
- 报告问题缺位置或影响或建议修复
- 鉴权/金额/并发/SQL/资源 未走查

## 十一、合格审查报告示例（精简）

```
# 代码审查报告（示例：任务服务）

## 1. 范围与目标
审查 TaskService/TaskController/Repository，对照需求 FR-2..FR-4、DB 设计 tasks 表、API v1 契约。

## 2. 静态分析
ESLint + Checkstyle 已跑，0 error；人工审查补充业务与鉴权维度。

## 3. Critical / Major
- [Critical] 位置：TaskController.java:35
  问题：deleteTask 未校验归属，任意登录用户可删他人任务（越权）。
  影响：水平越权，数据被非法删除，HIGH。
  建议修复：Service 层校验 task.user_id == currentUser.id，不匹配抛 Forbidden。
- [Major] 位置：UserService.java:88
  问题：catch Exception 后吞异常，无日志无响应，排查困难。
  影响：错误无法定位，用户看到 500 却无上下文。
  建议修复：记录结构化日志（含 traceId），按类型错误码返回。

## 4. Minor
- TaskService.java:150 魔法数字 3（默认状态）建议常量化。

## 5. Suggestions
- Repository 查询建议标注 @Param 提升可读性。

## 6. 重点风险区
- 鉴权：deleteTask 越权（见 Critical）。
- 金额：本项目无金额逻辑（已确认）。
- 并发：Task status 更新为单行 update，无并发问题。
- SQL：均走 Repository 参数化，无注入；需补任务列表 user_id+status 索引（对应 DB 设计）。
- 资源：Repository 用连接池自动管理，未发现问题。

## 7. 亮点
- 事务边界集中在 Service 层，范围控制得当；字段命名与 API 契约一致。

## 8. 结论
存在 1 Critical、1 Major → 不通过，**回退 development** 修复后重新审查。
```

## 常识

- 审查是质量闸门：宁可现在发现，也不要让缺陷进入测试与生产。
- 用证据说话：每条问题给出位置、问题、影响、建议修复，便于开发定位。
- Critical/Major 未清零一律回退，这是写死的闸门，不做例外。
