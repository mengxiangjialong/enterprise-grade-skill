# database-design

负责**数据库**设计。

## 最终目标

> 数据应该如何存储：结构清晰、可迁移、可维护，且承载真实查询。

## 一、强制输出（不可省略）

1. **表设计**：每张表每个字段强制包含——主键、类型、可空、默认值、注释、约束。
2. **关系与基数**：写清 1:1 / 1:N / N:M，外键策略明确。
3. **索引设计**：由查询场景驱动，说明为何建、避免过度索引。
4. **迁移策略**：版本化迁移、回滚、数据回填注意点。
5. **数据生命周期**：软删、归档、保留策略（若涉及）。
6. **字段映射**：与 API / 业务对象的字段映射关系。

## 二、输入与前置

- 输入：architecture-design（技术栈/底层库）、product-design（业务对象）、api-design 草稿方向。
- 实体来自需求/产品中的业务对象，映射自业务概念而非数据结构。

## 三、表设计：强制字段

每张表、每个字段都按下表逐项给出：

```
| 表名 | users（示例） |
| 字段 | 类型 | 可空 | 默认值 | 主键 | 约束 | 注释 |
| id | bigint | 否 | auto | PK | 自增 | 用户ID |
| email | varchar(255) | 否 | - | - | UNIQUE | 登录邮箱 |
| nickname | varchar(50) | 是 | NULL | - | - | 昵称 |
| status | tinyint | 否 | 1 | - | 1启用/0禁用 | 状态 |
```

- **主键**：明确单列/组合、类型、自增还是 UUID。
- **类型**：与业务匹配且节省空间（金额用 numeric，状态用 tinyint/int 枚举，时间用 timestamp with tz）。
- **可空 / 默认值**：显式给出，避免隐式 NULL 歧义。
- **注释**：说明业务含义，必要时标状态枚举取值。
- **约束**：唯一、非空、CHECK、外键。

## 四、关系与基数（写清 + 外键策略）

对每对实体关系写清基数与方式：

```
- 用户 1:N 任务（foreign key：tasks.user_id → users.id）
- 任务 N:M 标签（中间表 task_tags: task_id, tag_id，联合主键 + 唯一）
```

**外键策略**明确二选一并说明理由：
- 物理外键：保证引用完整性，但影响写入性能、组表迁移耦合。
- 应用层约束：性能好、解耦；需在代码/事务中保证一致性。
- 推荐：写入可靠、规模可控时可用物理外键；高写并发/拆分场景用应用层约束 + 一致性兜底。

## 五、索引设计：查询场景驱动

- **由真实查询驱动**：列出每个关键查询，说明为它建什么索引、为什么。
- 说明：组合索引的列顺序（按等值→范围）、是否覆盖索引、唯一索引。
- **避免过度索引**：只为存在的查询路径建，不为想象中的查询建；移除无收益索引；权衡写放大。

```
示例：
- 查询"按用户+状态筛选任务" → idx (user_id, status)：等值 user_id 在前。
- 查询"按截止日期范围" → idx (due_date)。
- 不索引：低频、选择性差的字段。
```

## 六、迁移策略（版本化 / 回滚 / 数据回填）

- **版本化**：每次变更一个版本号（如 V1__init.sql，V2__add_column.sql），按序应用，可追溯。
- **回滚**：每个迁移尽量有对应回滚思路（down 脚本或重建策略），大变更保留备份。
- **数据回填注意点**：
  - 先增列（可空/默认）→ 应用双写 → 回填 → 再收紧约束，避免一次性锁长。
  - 大批量回填分批执行，限速、可中断、可恢复。
  - 回填前后校验数据一致。

## 七、数据生命周期（软删 / 归档 / 保留策略）

若涉及数据留存，明确：

- **软删除**：`deleted_at` / `is_deleted` 标记；查询统一过滤；是否全局唯一涉及死列处理。
- **归档**：超期数据移到归档表/冷存储触发条件与时机。
- **保留策略**：数据留存多久、何时清理、由谁执行。
- 明确哪些走软删、哪些真正物理删除、哪些归档。

## 八、与 API / 业务对象的字段映射

- 提供 表字段 ↔ API 字段 / 业务对象字段 的映射，保证命名与语义对得上。
```
表 users.email  ↔  API user.Email / DTO email
表 tasks.status ↔  API task.status（枚举值定义一致）
```

## 九、范式与反范式取舍

- 默认满足 3NF 消除冗余与更新异常。
- 反范式触发器：高读低写、查询昂贵（如冗余统计字段）、需避免频繁 join。
- 反范式必须写明：冗余字段、为何反、一致性如何保证（应用补偿/定时同步）。

## 十、读写分离 / 分库分表（触发条件，避免过早）

- **默认不做**，只在出现明确信号时才引入：
  - 读写分离信号：读远多于写、主库读压力高。
  - 分库分表信号：单表数据量/写入超过单库承载、扩展已受限。
- 在这些信号出现前，不做分库分表；避免引入分布式复杂性过早。
- 若采用，说明路由键、扩容方式、跨片事务与一致性。

## 十一、敏感字段加密 / 脱敏设计点

- 识别敏感字段（密码、Token、手机、身份证等）。
- 策略：
  - **不可逆**（密码/密钥）：哈希（bcrypt/argon2），不存明文。
  - **可逆**（需回显如手机号）：应用层加密 + 密钥管理，不落库明文。
  - **脱敏**：日志、展示、导出默认脱敏（138****8000）。
  - 加密字段避免建立普通索引（高基数字段可考虑哈希列索引）。

## 十二、种子数据与测试数据策略

- **种子数据**（初始化必需，如枚举、默认配置）：随迁移或单独脚本，可重复执行（幂等）。
- **测试数据**：明确生成方式（工厂/脚本）、与生产隔离、不污染迁移校验。
- 严禁把种子/测试数据写成生产逻辑判断分支。

## 十三、输出

ALWAYS 使用以下结构生成数据库设计：

```
# 数据库设计
## 1. 实体清单与业务对象映射
## 2. ER 关系图（Mermaid，标注基数）
## 3. 表结构定义（每表每字段：主键/类型/可空/默认值/约束/注释）
## 4. 关系与基数、外键策略
## 5. 索引设计（查询场景驱动 + 为何建 + 避免过度）
## 6. 状态与时间字段约定
## 7. 数据生命周期（软删/归档/保留）
## 8. 迁移策略（版本化/回滚/数据回填）
## 9. 敏感字段加密 / 脱敏
## 10. 范式与反范式取舍、读写分离/分库分表触发条件
## 11. 种子数据与测试数据策略
## 12. 字段映射（表 ↔ API/业务对象）
## 13. 潜在问题与风险
```

## 十四、质量门槛

### 完成判定（全部满足才可进入下一阶段）

- [ ] **核心表完整**：主表与关联表的字段齐全，含主键/类型/可空/默认值/注释/约束
- [ ] 关系与基数清晰，外键策略明确
- [ ] **关键查询有索引依据**：每个核心查询路径有对应索引及建索引理由
- [ ] **迁移可回滚**：思路清晰（版本化 + up/down 或备份）
- [ ] 生命周期（若涉及软删/归档/保留）已明确
- [ ] 敏感字段有加密/脱敏方案
- [ ] 与 API/业务对象字段映射一致

### 不合格信号

- 字段缺类型/可空/默认值/注释/约束
- 关系无基数说明，外键策略含糊
- 索引无查询依据、为想象建索引或无覆盖率考虑
- 迁移不可回滚、无版本化
- 敏感字段明文存储且无方案
- 表字段与 API/业务对象对不上

## 十五、含 DDL 的设计示例（精简）

```
# 数据库设计（示例：任务管理）

## 1. 实体
User, Task, Tag

## 2. ER
graph LR
    User 1--N Task
    Task N--M Tag

## 3. 表结构
### users
| field | type | null | default | key | comment |
| id | bigint | no | auto | PK | 用户ID |
| email | varchar(255) | no | - | UQ | 邮箱 |
| pass_hash | varchar(100) | no | - | - | 密码哈希 |
| status | tinyint | no | 1 | - | 1启用0禁用 |

DDL（节选）：
CREATE TABLE users (
  id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '用户ID',
  email VARCHAR(255) NOT NULL UNIQUE COMMENT '邮箱',
  pass_hash VARCHAR(100) NOT NULL COMMENT '密码哈希',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '1启用0禁用'
) COMMENT '用户表';

### tasks
| id | ... | status | ... |
CREATE TABLE tasks (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT NOT NULL COMMENT '所属用户',
  title VARCHAR(200) NOT NULL,
  status TINYINT NOT NULL DEFAULT 0 COMMENT '0待办1进行中2完成',
  due_date DATE NULL,
  INDEX idx_user_status (user_id, status),  -- 覆盖"按用户+状态筛选"
  INDEX idx_due (due_date)                 -- 覆盖"按到期范围"
) COMMENT '任务表';

## 5. 索引依据
- 查询"我的任务按状态筛选" → idx_user_status（等值 user_id 在前）。
- 查询"到期任务" → idx_due。
- 未为低频/低选择性字段建索引，避免过度。

## 8. 迁移
V1__init.sql (up/down)；加列走"先加可空列→应用双写→回填→收紧约束"。

## 9. 敏感字段
- pass_hash 用 bcrypt，逆不可。
- email 非明文展示在日志与列表，默认脱敏。

## 12. 字段映射
- users.email ↔ DTO User.email
- tasks.status ↔ API task.status（0/1/2 枚举一致）
```

## 常识

- 数据库一旦上线，迁移成本高：设计阶段多花时间值得。
- 从真实查询出发建索引，符合 80/20 法则，不为其想象中的每个查询建索引。
- 过度索引与过度分库都是负资产：以真实信号为准。
