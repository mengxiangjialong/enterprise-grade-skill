# database-design

负责**数据库**设计。

## 最终目标

> 数据应该如何存储。

## 设计内容

- **实体识别**：从需求/产品中识别出域实体与属性
- **数据关系**：一对多 / 多对多 / 一对一，用 ER 描述
- **表结构**：每张表的字段集合
- **字段设计**：命名、类型、默认值、可空性、业务含义
- **主键**：单列 / 组合，类型选择
- **外键**：关系如何表达（物理外键 / 应用层约束）
- **唯一约束**：哪些字段组合唯一
- **索引**：加速哪些查询，覆盖率如何
- **数据类型**：与业务匹配且节省空间
- **状态字段**：状态枚举的表示方式
- **时间字段**：创建/更新时间、时区处理
- **软删除**：是否需要，如何实现
- **数据冗余**：是否冗余以换取读性能，如何保证一致性
- **数据扩展性**：为未来字段与数据量预留空间

## 设计检查（Review Checklist）

完成设计时逐项检查：

- 是否存在**缺失索引**（查询路径上无索引）
- 是否存在**重复数据**（冗余无必要导致不一致）
- 是否存在**不合理的数据关系**
- 是否可能出现 **N+1 查询**（需确认关联加载策略）
- 是否考虑**未来数据增长**（量级、分区、归档）
- 字段取值是否是确定的数值语义（如状态、金额）而不是字符串拼接

## 设计原则

- **以查询与业务为主设计**，围绕真实访问模式建立索引与结构。
- **合理使用约束**能避免脏数据，但不过度使用外键影响写性能（需权衡）。
- **一致性优于过度冗余**：冗余要明确同步机制。

## 输出

ALWAYS 使用以下结构生成数据库设计：

```
# 数据库设计
## 1. 实体清单
## 2. ER 关系图（Mermaid 或文字描述）
## 3. 表结构定义（每表：字段名/类型/约束/默认值/说明）
## 4. 主键与唯一约束
## 5. 索引设计（含覆盖索引与组合索引理由）
## 6. 状态与时间字段约定
## 7. 软删除 / 审计字段
## 8. 数据冗余与一致性说明
## 9. 扩展与演进（容量、分区、归档）
## 10. 潜在问题与风险（N+1、缺失索引等）
```

## 常识

- 数据库一旦上线，迁移成本高：设计阶段多花时间值得。
- 从真实查询出发建索引，符合 80/20 法则，不要为想象中的每个查询建索引。
