# debugging

专门负责 **Bug 定位和修复**。

## 最终目标

> 修复根因，而不是只处理表面错误；根因明确、改动最小、回归通过。

## 〇、执行边界与指令优先级

> **用户显式指令优先于本技能指南。** 用户要求与以下冲突时，按用户要求执行并说明差异。

- **输入**：testing 的失败交接清单，或用户/运行时报错的描述、日志、堆栈。
- **步骤**：复现 → 证据 → 假设 → 验证 → 根因 → 最小修复 → 回归。
- **输出**：含复现步骤与回归结果的排查报告；若根因在设计层则触发回退。
- **不可臆测**：不"看到报错就改"；未经复现与验证不得宣布修复。
- **何时停止**：无法复现时不谎称已修复；根因在需求/设计层时回退对应阶段而非打补丁。
- **支持文件**：复现/取证模板可放 references/，从 SKILL.md 引用并注明何时使用。

## 一、标准流程（强制顺序，不可跳步）

严格按以下顺序执行，每步有明确输出：

```
复现 Bug        能稳定复现或拿到复现路径/输入
  ↓
收集证据        日志、堆栈、现象、数据（用证据说话）
  ↓
提出假设        列出可能的根因（可验证的假设）
  ↓
验证假设        逐一验证，排除非根因
  ↓
找到根因        确定真实原因
  ↓
最小修复        只改与根因相关的部分
  ↓
回归测试        复现用例 + 相关测试通过
```

顺序不可跳步：未复现就改、未验证就下结论，都是违规。

## 二、禁止行为（写死）

> **禁止"看到报错就改"的错误循环。**

```
看到报错
  ↓
随便修改代码      ← 禁止
  ↓
出现新的 Bug
  ↓
继续修改          ← 禁止（反复堆叠，越修越糟）
```

- 禁止未复现就盲目改代码。
- 禁止凭直觉猜、一次性堆大量改动。
- 禁止跳过证据收集/假设验证直接改。

## 三、根因分层与回退规则（强制）

- 先判断根因属于哪一层：
  - **需求层**：需求本身有问题/歧义
  - **设计层**：产品/架构/DB/API/UI 设计缺陷
  - **实现层**：编码错误
- 若根因在**需求/设计层** → **必须触发回退到对应阶段**修正设计，**禁止只打代码补丁**绕过问题。
- 实现层根因 → 本阶段最小修复。
- 回退遵循最小回溯：只回到根因所在阶段，修复后重跑受影响下游。

## 四、报告必须含（强制）

- **复现步骤**：稳定或尽量复现的路径/输入。
- **回归结果**：修复后复现用例 + 相关测试通过情况。
- 缺少复现步骤或回归结果即视为报告不完整。

## 五、常见根因类别 + 定位线索示例

- **逻辑错误**（条件、循环、边界）
  线索：某输入组合下走错分支；构造等价类 vs 边界输入对照。
- **数据/类型问题**（空值、格式、精度、时区）
  线索：NullPointer / 金额精度差 / UTC+本地时区偏移；打印中间值比对。
- **并发问题**（竞态、死锁、线程安全）
  线索：仅在高峰多请求出现；破坏性复现（压测并发修改同一数据）。
- **外部依赖**（接口变更、超时、配置、网络）
  线索：错误信息含第三方返回异常；对比接口文档/配置前后差异；超时曲线。
- **资源问题**（泄漏、连接耗尽、内存）
  线索：运行一段时间后变慢/报连接超时；监控连接数/内存持续上升。
- **权限/鉴权问题**
  线索：某些角色/环境下行为异常；核对权限矩阵与调用上下文。

## 六、无法稳定复现时的处理策略

- **日志增强**：在可疑路径补关键上下文日志（入参/中间值/分支命中），带 traceId 串联，再收集。
- **采样/特征抓取**：对线上按采样或命中特征（用户、TraceId、失败码）抓取上下文，缩小范围。
- **灰度复现**：疑似环境/配置相关，在与线上接近的灰度环境复现对照。
- 无法复现时，不盲目下结论"已修复"，要记录"复现未成功 + 已做的取证"，持续观察。

## 七、修复与测试用例的双向绑定（防回归）

- 对每个根因修复，**先写/更新一个可复现该 Bug 的测试用例**（红），再修复（绿），最后跑相关回归。
- 修复与之绑定：`修复描述 ↔ 复现用例 TC-xxx`。
- 目的是让该 Bug 成为永久回归防线，不复出现。

```
写复现用例(红) → 修复(绿) → 关联回归 绑定：fix-for-BugX ↔ TC-003
```

## 八、输出

ALWAYS 使用以下结构生成排查报告：

```
# Bug 排查报告
## 1. 问题描述与影响
## 2. 复现步骤
## 3. 收集到的证据（日志/堆栈/现象/数据）
## 4. 定位过程（假设 + 验证，含排除）
## 5. 根因分析（指出所属层：需求/设计/实现）
## 6. 修复方案（最小改动说明）
## 7. 回归测试结果（复现用例 + 相关测试）
## 8. 结论（是否修复完成 / 是否需回退对应阶段）
```

## 九、质量门槛

### 完成判定（全部满足）

- [ ] **根因明确**（能说清真实原因，非猜测）
- [ ] **改动最小**（只改根因相关）
- [ ] **回归通过**（复现用例 + 相关测试通过）
- [ ] 报告含**复现步骤**与**回归结果**
- [ ] 根因在需求/设计层时已**回退对应阶段**（未只打补丁）
- [ ] 修复与复现用例**双向绑定**（防回归）

### 不合格信号

- 未复现就改/宣布修复
- 陷入"看到报错就改"循环
- 根因在设计/需求层却只打代码补丁
- 无复现步骤或回归结果
- 改动过大、夹带无关修改
- 无测试用例兜底该 Bug

## 十、合格排查报告示例（精简）

```
# Bug 排查报告（示例）

## 1. 问题描述与影响
用户 B 可删除用户 A 的任务（越权），影响数据安全，HIGH。

## 2. 复现步骤
1) 用户 A 创建任务 id=10；2) 用户 B 调用 DELETE /api/v1/tasks/10；3) 返回 200 且任务被删。

## 3. 证据
- 接口日志：B 删除成功，无鉴权拦截。
- 代码：TaskService.delete 未校验 task.user_id == currentUser.id。

## 4. 定位过程
假设1：Controller 缺注解 → 已拦截，排除。
假设2：Service 缺归属校验 → 代码确认无 user_id 比较，命中。

## 5. 根因分析
层级：实现层（开发遗漏归属校验）。鉴权/权限规则产品明确（BR-3），非设计缺口。

## 6. 修复方案（最小改动）
TaskService.delete 增加：task.user_id != currentUser.id 则抛 Forbidden。
（仅改此处，未涉其余。）

## 7. 回归测试结果
- 复现用例 TC-003（B 删 A 的任务）→ 修复前红 / 修复后绿。
- 相关测试：delete 正常、无权限、404 全部通过（12 passed, 0 failed）。

## 8. 结论
根因明确、改动最小、回归通过，修复完成。绑定：TC-003 作为防回归用例。
```

## 常识

- 调试的本质是"缩小不确定区间"：每条证据都在排除假设。
- 根因在哪一层，就在哪一层修：需求/设计层的病，代码补丁治不好。
- 让每个 Bug 都变成一条永久回归用例，是对未来最大的保护。
