# debugging

专门负责 **Bug 定位和修复**。

## 最终目标

> 修复根因，而不是只处理表面错误。

## 标准流程

严格按以下顺序执行：

```
发现 Bug
  ↓
复现 Bug
  ↓
收集日志
  ↓
定位问题
  ↓
提出假设
  ↓
验证假设
  ↓
找到根因
  ↓
最小修改
  ↓
回归测试
```

## 要避免的错误循环

不要陷入：

```
看到报错
  ↓
随便修改代码
  ↓
出现新的 Bug
  ↓
继续修改  ← 反复堆叠，越修越糟
```

## 排查要则

- **先复现**：不能复现的 Bug 很难确认修复有效。尽量稳定复现路径/输入。
- **用证据定位**：读日志、报错栈、数据与代码，找到真实根因，而非凭直觉猜。
- **先假设后验证**：对每个可能的根因提出可验证的假设，逐一排除。
- **最小修改**：只改动与根因相关的部分，不引入无关改动。
- **修复后回归**：运行复现用例与相关测试，确认修复且无回归。

## 常见根因类别

排查时按类别定位：

- 逻辑错误（条件、循环、边界）
- 数据/类型问题（空值、格式、精度、时区）
- 并发问题（竞态、死锁、线程安全）
- 外部依赖（接口变更、超时、配置、网络）
- 资源问题（泄漏、连接耗尽、内存）
- 权限/鉴权问题

## 输出

ALWAYS 使用以下结构生成排查报告：

```
# Bug 排查报告
## 1. 问题描述与影响
## 2. 复现步骤
## 3. 收集到的证据（日志、堆栈、现象）
## 4. 定位过程（假设 + 验证）
## 5. 根因分析
## 6. 修复方案（最小改动说明）
## 7. 回归测试结果
## 8. 结论
```

## 常识

- 调试的本质是"缩小不确定区间"：每一条证据都在帮助排除假设。
- 若根因在设计/需求层（而非代码层），把发现反馈给相应阶段，不要只在代码上打补丁。
