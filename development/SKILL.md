# development

真正负责**代码开发**。

## 最终目标

> 把设计写成可运行的代码，且实现可对齐设计、可被验证、可顺利交接。

## 一、硬规则（必须遵守）

> **未读设计文档，不得编码。**

在写任何生产代码**之前**，必须先完成设计文档阅读并记录。没有完成阅读记录而直接编码，视为违规，第一阶段判定为未完成。

## 二、编码前强制阅读清单 + 已读记录（强制）

动手编码前 ALWAYS 阅读以下设计文档，并在开发记录里逐项**标记已读**与实际结论：

```
- [ ] requirements    需求规格（要做什么、验收标准）
- [ ] product design  产品方案（功能、流程、五态、权限矩阵）
- [ ] architecture    架构设计（技术栈、目录、模块边界）
- [ ] database        数据库设计（表结构、字段映射）
- [ ] api             API 设计（接口契约、字段）
- [ ] ui              UI 设计（页面、交互、数据绑定）
```

阅读完成后记录：`已读文档列表 + 每份关键结论（一两句）`，作为后续对齐与交接依据。缺一份即视为"未读齐"，不得编码。

## 三、编码前必读 → 各文档对齐要点

| 文档 | 编码时对齐要点 |
| ---- | -------------- |
| requirements | 只实现范围内需求，未关闭问题不臆测 |
| product design | 页面/流程/状态按产品做，不擅自增删 |
| architecture | 目录、分层、模块边界、依赖方向照架构做 |
| database | 表结构、迁移、字段映射与 DB 设计一致 |
| api | 接口地址、参数、响应、错误码照契约实现 |
| ui | 页面结构、交互、数据绑定照 UI 设计实现 |

## 四、禁止行为清单（强化）

- **未读设计直接编码**（硬规则）
- **擅自修改设计**：不读需求/产品/架构/API/UI 就改结构、接口、页面行为
- **引入无关大重构**：为解决一个小问题顺带大改无关模块
- **为解决问题堆无关代码**：一处故障塞入大量不相干逻辑
- **没有验证就宣布完成**：未编译/未运行/未测就说"做完了"
- **无视架构约束**：破坏依赖方向、模块边界、命名约定

### 确需偏离设计时
- 先说明**理由**与**影响**，记录下来；能改设计阶段的改设计阶段，而不是在代码里悄悄改。

## 五、增量交付节奏（强制）

- 每完成一个**可独立验证的模块/功能点**，立即做一次验证，而不是攒到最后一次性"我全写完了"。
- 验证至少包含：**可编译 / 可运行**。
- 逐模块确认无误再进入下一个模块，缩小出错面，便于定位。

```
模块 A：写代码 → 编译 → 运行冒烟 → OK
模块 B：写代码 → 编译 → 运行冒烟 → OK
...
```

## 六、测试最低要求（强制）

- 对**复杂逻辑、边界条件、异常路径、鉴权/金额/并发**等关键路径，必须有测试。
- 至少：核心业务逻辑单元测试；关键集成点集成测试。
- 测试要可重复执行（不依赖环境随机状态）。
- 暂未覆盖的高风险点要登记，不得"明知没测却宣称完成"。

## 七、完成证据（强制记录方式）

每个模块/整体交付时，用可核查的方式记录：

- **编译通过**：命令 + 结果（exit code / 无报错的输出片段）
- **本地启动**：启动命令 + 服务可访问的证据（日志/健康检查/页面可打开）
- **相关测试通过**：运行相关测试命令 + 通过数/失败数

```
模块 A 完成证据：
- 编译：gradle compileJava → BUILD SUCCESSFUL
- 运行：./gradlew bootRun → Started Application；GET /health → 200
- 测试：./gradlew test --tests TaskServiceTest → 12 passed, 0 failed
```

无上述证据的功能点不得标记完成。

## 八、建议增强

### 目录与命名与 architecture 一致（检查项）
- 对照架构设计的目录结构，必须创建一致的目录与命名，不做即兴结构。
- 命名（包、类、文件）与架构/代码约定一致。

### 环境变量与配置接入检查
- 读取配置的来源（环境变量/配置文件/密钥服务），**不硬编码**数据库地址、密钥。
- 本地、测试、生产用不同配置来源，编码时验证配置可注入、无硬编码。

### 已知技术债登记
- 临时妥协（如跳过某边界、用同步代替异步、简化校验）要**登记**：妥协点、原因、影响、计划补齐时间。
- 不得将技术债悄悄留在代码里而不说明。

### 与 code-review 的交接清单
交付 code-review 前整理：
- **改动范围**：改了哪些模块/文件/接口
- **风险点**：哪些地方容易出错、边界、并发、鉴权
- **未覆盖**：未写测试或未验证的路径
- **技术债**：临时妥协清单
- **设计偏离**：所记录的偏离理由与影响

## 九、输出 / 开发记录结构

开发过程记录建议包含：

```
# 开发记录
## 1. 设计已读清单（逐项勾选 + 关键结论）
## 2. 开发范围与模块划分
## 3. 模块开发与验证日志（逐模块：完成项/编译/运行/测试）
## 4. 配置与环境接入情况
## 5. 已知技术债登记
## 6. 完成证据汇总（编译/启动/测试）
## 7. 交接清单（改动范围、风险点、未覆盖、设计偏离）
```

## 十、质量门槛

### 完成判定（全部满足）

- [ ] **设计已读清单齐全**（需求/产品/架构/DB/API/UI 均已读并记录）
- [ ] 实现与各设计**对齐**（目录、接口、字段、行为无冲突）
- [ ] **可运行**：本地启动成功
- [ ] **关键路径有验证证据**：编译通过 + 相关测试通过
- [ ] 无未登记的**设计偏离/技术债**
- [ ] 已准备 **code-review 交接清单**

### 不合格信号

- 未完成设计阅读记录就产出代码
- 擅自改动设计/引入无关大重构
- 中断式交付——一次性堆一大段代码无中间验证
- 关键逻辑无测试
- 无编译/运行/测试证据就宣称完成
- 存在未登记的技术债或设计偏离

## 十一、常识

- 编码只是流水线一环：忠实还原设计，能让 code-review、testing 省力。
- 宁可慢一点把基础打牢，也不要堆砌出难以维护的代码。
- 完成 = 设计对齐 + 可运行 + 有验证证据，三者缺一不可。
