# documentation

负责项目**文档**。

## 最终目标

> 一位新人（开发者/使用者/运维）拿到项目后，能**照着文档跑起来**并完成一次主流程验证。

## 一、文档范围清单（强制，按需生成）

```
README.md        项目入口 / 快速开始
QUICKSTART.md    快速开始（可选并入 README）
ARCHITECTURE.md  架构摘要
API.md           API 说明
DEPLOYMENT.md    运维 / 部署
CONFIGURATION.md 配置说明
DEVELOPMENT.md   开发指南（可选）
CHANGELOG.md     变更日志
FAQ.md           故障排查 / 常见问题
```

至少产出：**README、快速开始、架构摘要、API 说明、运维/部署、配置说明**。其余按项目规模选用。

## 二、README 最低结构（强制）

README 必须包含以下五块（缺一即不达标）：

1. **项目是什么**：背景、目标、核心功能（一两句能让新人判断这是什么）。
2. **如何运行**：环境要求 + 安装 + 启动命令（可复制执行）。
3. **如何配置**：配置文件 / 环境变量说明，必需项标注。
4. **如何测试**：运行相关测试的命令与说明。
5. **目录说明**：关键目录/模块作用（让新人知道代码在哪、怎么组织）。

## 三、快速开始

- 最短可行路径：从 clone 到 "跑起来 + 完成一次主流程"（如创建并查看一条数据）。
- 只写必要步骤；每步命令必须可复制、与真实实现一致。

## 四、架构摘要

- 简明说明：技术栈、模块/服务、数据流、关键交互（可引用架构文档/架构图）。
- 不必重复完整架构设计，给出摘要 + 引用链接即可。

## 五、API 说明

- 接口清单：方法/路径/鉴权/关键请求与响应示例/错误码说明。
- 内容与 api-design 契约一致；提供指向详细契约（OpenAPI）的链接。

## 六、运维 / 部署

- 构建、发布、环境（dev/staging/prod）；启动与停止、健康检查、日志位置、备份/回滚要点。
- 配置项随环境差异的说明。

## 七、配置说明

- 配置文件位置、每个配置项的用途、必需/可选、是否涉及密钥（密钥应走环境变量/密钥服务，文档不写明文）。
- 给出 `.env.example` 或配置清单模板。

## 八、与真实实现一致（强制硬约束）

> **文档与代码脱节 = 文档不合格。**

- 命令、路径、配置、字段、端口、依赖版本必须与真实项目一致，可被直接执行/核验。
- 不写臆造内容；写完对照代码走查，任何不一致必须修正。
- 文档中出现的每个命令最好实际跑一遍验证其可执行。

## 九、关键决策可引用 ADR / 架构文档（强制）

- 涉及关键决策（技术选型、架构取舍、为何"选 A 不选 B"）处，**引用 ADR 或架构文档链接**，而不在 README 里重复堆理由。
- 保持单一来源：README 告知"为什么这么设计→见 ADR-x/ARCHITECTURE.md"，细节指向原文。

## 十、建议增强

### 面向角色的文档分流（开发者/使用者/运维）
- **开发者**：DEVELOPMENT.md——目录、约定、构建测试、如何改代码。
- **使用者/调用方**：API.md、QUICKSTART——怎么调/怎么用。
- **运维**：DEPLOYMENT.md、CONFIGURATION.md、FAQ——怎么跑/怎么配/怎么排障。
- 按读者入口组织导航，避免人人从全长文档找信息。

### 变更日志（Changelog）模板
```
# Changelog
## [版本号] - YYYY-MM-DD
### Added     新增功能
### Changed   变更
### Fixed     修复
### Deprecated 弃用
### Removed   移除
```
- 记录对本版本用户有影响的变化；重大不兼容单独标注。

### 故障排查常见问题（FAQ）
- 收集停用踩点：安装失败、端口占用、配置缺失、连不上数据库、鉴权/权限报错等。
- 每条：现象 → 原因 → 解法。

### 截图或命令示例的最低要求
- 涉及关键界面/结果处附**截图**或**命令输出示例**，帮助读者对照确认操作正确。
- 至少：能证明"主流程验证成功"的一处示例（命令输出 / 页面截图）。

## 十一、输出

以 README 为入口 + 独立文档，遵循"README 够用、细节进独立文档 + 引用链接"。

## 十二、质量门槛

### 完成判定（全部满足）

- [ ] **新人按文档可完成安装**：clone → 装依赖 → 启动 全程可照做
- [ ] **可完成一次主流程验证**：照文档能跑通一次核心流程
- [ ] README 五块结构齐全（是什么/如何运行/如何配置/如何测试/目录）
- [ ] 文档范围覆盖六类（README/快速开始/架构/API/运维/配置）
- [ ] **与真实实现一致**（命令/路径/配置可核验，无臆造）
- [ ] 文档与代码走查无脱节

### 不合格信号

- README 缺"如何配置"或"如何测试"等关键块
- 命令/路径/配置与真实实现不符
- 只有架构摘要/API 却无快速开始、部署、配置
- 关键决策无 ADR/架构引用，或引用空洞
- 新人照文档跑不起来（无法完成安装或主流程）

## 十三、合格 README 大纲示例（精简）

```
# 任务服务 (Task Service)

## 项目是什么
一个多用户的待办任务服务：创建/查看/完成/删除任务，带用户鉴权与归属控制。
技术栈：Spring Boot 3 + PostgreSQL + React。

## 环境要求
- JDK 17
- Node 18+
- PostgreSQL 14+

## 如何运行
1) clone 到本地
   git clone <repo> && cd task-service
2) 安装依赖
   ./gradlew build
   （前端：npm install）
3) 初始化数据库
   ./gradlew migrate (应用 src/main/resources/db/migration 下的迁移)
4) 启动
   ./gradlew bootRun
   （前端：npm run dev）
   验证 http://localhost:8080/api/health → 返回 {"status":"ok"}

## 如何配置
复制 .env.example 为 .env 并填写（值见各注释）：
- DB_URL / DB_USER / DB_PASSWORD
- JWT_SECRET（密钥，勿提交仓库）
其余配置项见 CONFIGURATION.md。

## 如何测试
后端：./gradlew test （当前 42 passed / 0 failed）
前端：npm test

## 目录说明
- src/main/java：后端源码（controller/service/repository 分层）
- src/main/resources/db/migration：数据库迁移
- web/：前端 React 应用
- docs/: 架构摘要、API、部署、FAQ（见下方文档导航）

## 文档导航
- 快速开始：QUICKSTART.md
- 架构摘要：ARCHITECTURE.md
- API：API.md
- 运维部署：DEPLOYMENT.md
- 配置：CONFIGURATION.md
- 变更：CHANGELOG.md | 排障：FAQ.md
```

> 关键决策（如"为何用 PostgreSQL / 单服务"）→ 引用 `docs/ADR-001.md`。

## 常识

- 好文档能降低团队上手与沟通成本，是项目的"隐性资产"。
- 文档随代码演进，保持同步比一次性写全更重要。
- 文档写没写好，看新人能不能照跑一遍主流程验证。
