# performance-optimization

负责**性能分析与优化**。

## 最终目标

> 定位性能瓶颈并优化，以**可量化、可对比**的数据衡量效果。

## 〇、执行边界与指令优先级

> **用户显式指令优先于本技能指南。** 用户要求与以下冲突时，按用户要求执行并说明差异。

- **输入**：疑似性能问题的接口/页面/查询的定位请求或压测诉求。
- **步骤**：测量（基准）→ 定位 → 方案 → 修改 → 复测 → 对比。
- **输出**：含同环境前后对比数据的性能报告（收益可量化）。
- **不可臆测**：无基准数据不得优化（硬规则）；不无脑缓存/加索引。
- **何时停止**：无感知收益或无容量问题时不优化；架构级瓶颈回退 architecture。
- **支持文件**：压测脚本/命令可放 scripts/ 或 references/，从 SKILL.md 引用并注明何时运行。

## 一、硬规则

> **无基准数据，不得优化。**

- 未先拿到现状基准数据（耗时/吞吐/资源占用）之前，禁止动手改代码。
- 任何"我觉得慢"而没有数据支撑的优化，视为违规且可回退。
- 优化以证据驱动，不以直觉驱动。

## 二、流程强制（顺序不可跳）

```
测量         拿到基准：耗时、吞吐、CPU/内存/IO、慢 SQL
  ↓
定位         用 profiling/指标/调用链找到真实瓶颈
  ↓
方案         针对瓶颈制定优化方案
  ↓
修改         最小改动，不动无关部分
  ↓
复测         同一条件、同一环境复测
  ↓
对比         优化前后数据对比，量化收益
```

## 三、报告必须含对比数据（强制）

- **优化前后必须在同一环境条件下对比**（同一机器/部署、同一压测脚本、同一数据集），否则对比无效。
- 报告记录：环境说明 + 指标项 + 优化前值 + 优化后值 + 提升比例。
- 没有同一环境的 raw 数据，不得宣称"优化成功"。

```
环境：8C/16G，Linux，并发 200，数据集 10w 行。
指标：P95 延迟 优化前 950ms → 优化后 210ms（↓78%）
      吞吐  优化前 120 rps → 优化后 480 rps（↑4x）
```

## 四、三类瓶颈的定位入口（强制）

按层定位，给入口方法：

### 前端
- 定位入口：浏览器 **Performance / Network / Lighthouse**；看首屏、资源体积、阻塞脚本、请求数、图片体积。
- 关注：FCP/LCP、JS 包体、渲染阻塞、瀑布图长请求、图片未懒加载。

### 后端
- 定位入口：**APM / profiling（CPU、内存）/ 应用日志耗时 / 调用链**；看慢接口、CPU 热点、GC/内存、线程池打满、IO 等待。
- 关注：慢端点、热点方法、连接池、锁与串行、日志刷盘。

### 数据库
- 定位入口：**慢查询日志 + EXPLAIN 查询计划**；看全表扫描、无索引、N+1、锁等待、磁盘 IO。
- 关注：无索引的 WHERE/JOIN/ORDER BY、扫描行数、sort filesort、长事务锁。

## 五、建议增强

### 常见优化手段按「适用场景」列出（不无脑缓存/加索引）

- **缓存**：适合"读多写少、数据变化不频繁、允许略延迟"；不适合实时强一致、低命中率。
  场景举例：热点配置、用户详情读取。
- **加索引**：适合"高频 WHERE/JOIN/ORDER BY 且选择性高"；不适合低选择性列、写密集表滥用。
  场景举例：按 user_id 查列表；不适合加在某标志位高重复列。
- **异步化**：适合"调用方不关心结果、可接受异步"；不适合必须同步返回强一致的链路。
- **连接池/并发调优**：适合"连接频繁创建、并发打满"；需压测确定池大小。
- **查询改写**：适合"多表 N+1、重复查询、大字段连带"；改前用 EXPLAIN 验证。
- **前端资源优化**：适合"包体大、图片多、请求数多"；量化后再懒加载/压缩/拆包。

### 过度优化的禁止信号

出现以下信号即停止/不执行该优化：
- **无用户可感知收益**：P99 从 30ms 降到 28ms，用户无感，不值得动。
- **无容量问题**：当前与可预见未来都不存在压测/容量压力，不预优化。
- 为优化引入了复杂度、缓存一致性风险或无关大改却没有数据收益。

### 与 architecture 扩展方案的衔接

- 当单点微调收益见顶、但瓶颈是**架构层面**（如单库写吞吐、无伸缩、同步强耦合）时，停止微调，**触发回退/衔接 architecture-data扩展方案**。
- 明确划线：`在现有架构内能做到什么程度；超出 → 交给 architecture 做架构级改造`。
- 微调 ≠ 架构改造：本阶段只做分层/局部优化；需要水平扩容、分库分表、异步事件化等应回退到 architecture 阶段设计并记录。

## 六、输出

ALWAYS 使用以下结构生成性能报告：

```
# 性能分析与优化报告
## 1. 问题描述与指标
## 2. 测量方法与环境（基准数据，同环境说明）
## 3. 瓶颈定位（前端/后端/数据库，入口与数据/调用链）
## 4. 优化方案（针对瓶颈，适用场景说明，排除过度优化）
## 5. 改动说明（最小改动）
## 6. Benchmark 结果（优化前后同一环境对比）
## 7. 结论与后续建议（收益量化；是否需转 architecture）
```

## 七、质量门槛

### 完成判定（全部满足）

- [ ] **瓶颈有数据支撑**（非猜测，有测量/定位数据）
- [ ] **收益可量化**（同环境前后对比，提升有数据）
- [ ] **无无关大改**（改动聚焦瓶颈，未夹带重构）
- [ ] 测量→定位→方案→修改→复测→对比流程完整
- [ ] 无数据即动的违规行为已剔除
- [ ] 过度优化信号已停止；架构级需求已衔接 architecture

### 不合格信号

- 无基准数据就改代码
- 报告缺优化前后对比，或前后环境/条件不一致
- 瓶颈靠"感觉"而非数据
- 改动涵盖大量无关模块
- 无脑加缓存/加索引而未说明适用场景

## 八、含前后对比的性能报告示例（精简）

```
# 性能分析与优化报告（示例：任务列表接口）

## 1. 问题
GET /api/v1/tasks 在 10w 数据、并发 200 下响应慢，P95 950ms。

## 2. 测量方法与环境
环境：8C/16G Linux，同一容器，wrk 并发 200，30s，数据集 10w 行。
基准：P95 950ms，吞吐 120 rps。

## 3. 瓶颈定位（数据库）
慢查询日志命中该接口 SQL；EXPLAIN 见 status+user_id 全表扫描 10w 行；无 N+1。

## 4. 优化方案（针对瓶颈，非无脑）
加 (user_id, status) 复合索引（WHERE 顺序一致、选择性高，适用）。不使用缓存：列表强一致且写频繁，缓存收益低（排除过度优化）。

## 5. 改动说明
仅新增索引 migration，无应用代码改动。

## 6. Benchmark（同一环境）
指标：P95 950ms → 210ms（↓78%）；吞吐 120 → 480 rps（↑4x）；EXPLAIN 扫描行 10w → 320。

## 7. 结论
瓶颈有数据支撑、收益可量化、改动最小。若后续数据单库写吞吐成为瓶颈，再衔接 architecture 评估读写分离/分片。
```

## 常识

- 优化要有收益边界：只优化真实瓶颈，避免过度优化。
- 每次优化都要能回答"数据上提升了多少"，且在同一环境下诚实对比。
- 微调到顶就交给 architecture，不拿代码层硬扛架构级问题。
