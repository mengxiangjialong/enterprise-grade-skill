# product-design

将需求转换成**完整的产品方案**，明确"用户如何使用这个系统"。

## 最终目标

> 用户如何使用这个系统，且每一部分都可被后续设计号、开发、测试照做。

## 一、强制输出（不可省略）

产出产品方案时**必须包含**以下四类：

1. **功能模块图**：功能模块划分及相互关系（给出图或 Mermaid）。
2. **信息架构**：页面结构、层级与导航关系。
3. **关键用户流程（含分支）**：用流程图描述，包含主路径 + 判断分支 + 异常分支，而非单线 happy path。
4. **角色 × 功能权限矩阵**：每个角色 × 每个功能/页面的权限（详见第六节）。

同时必须：

- 每个核心页面补齐**五态**（详见第五节）
- 业务流程用**状态机**描述（状态、事件、转移条件，详见第七节）
- 建立与 requirements 的**追溯关系**（模块/流程对应需求编号，详见第八节）

## 二、输入与前置

- 输入：requirements-analysis 产出的需求规格说明。
- 若缺少需求规格或其相关维度未关闭，先回到需求阶段，不擅自补全。

## 三、功能模块图

- 将需求按职责拆分为清晰的功能模块。
- 用 Mermaid 或结构图表达模块间关系（依赖、组合、并列）。
- 每个模块对应到若干需求编号。

示例（Mermaid 模块图）：
```
graph TD
    Auth[认证模块] --> Core[任务核心]
    Core --> B[看板模块]
    Core --> S[筛选统计]
```

| 模块 | 职责 | 关联需求 |
| ---- | ---- | -------- |
| 认证模块 | 登录/鉴权 | FR-1 |
| 任务核心 | 任务 CRUD/状态转换 | FR-2..FR-4 |
| 看板模块 | 看板视图 | FR-5 |

## 四、信息架构

- 页面清单与层级关系、导航结构、页面间跳转。
- 用树状结构或 Mermaid 展示。

```
├── 登录页
└── 主框架
    ├── 任务列表页
    │   ├── 新建任务（Dialog）
    │   └── 任务详情
    ├── 看板页
    └── 设置页
```

## 五、每个核心页面补齐五态

对每个核心页面，明确以下五种状态下的呈现与引导：

```
正常状态    数据完整可用
加载状态    数据获取中（骨架屏/loading）
空状态      无数据呈现 + 引导（如"去创建第一个任务"）
错误状态    请求失败呈现 + 重试
无权限状态  无访问权限的呈现与引导
```

模板：
```
### 页面：任务列表
- 正常：展示任务表格，支持状态筛选。
- 加载：列表区显示骨架屏。
- 空：显示"暂无任务，点此创建"。
- 错误：显示"加载失败，重试"按钮。
- 无权限：显示"无访问权限" + 返回首页。
```

## 六、角色 × 功能权限矩阵（强制）

- 列出全部角色与全部功能/页面，逐格标注权限：`√`（可访问/可操作）、`–`（不可）、`读写/只读` 等。
- **关键角色不允许留空白**：任何关键角色在该矩阵中都必须有明确结论。
- 矩阵应在后续 ui-design 与 development 中被直接引用。

```
# 权限矩阵
功能\角色 | 成员 | 管理员
登录      | √    | √
创建任务  | √    | √
删除任务  | 仅自己的 | 全部
管理成员  | –    | √
```

## 七、业务流程用状态机描述（强制）

- 对关键业务实体，用**状态机**描述，明确：**状态 / 事件 / 转移条件**。
- 非简单地写一句话流程，而是给出状态集合、驱动事件、迁移条件。

示例（Mermaid 状态图）：
```
stateDiagram-v2
    [*] --> 草稿
    草稿 --> 进行中: 开始任务(条件：标题完整)
    进行中 --> 已完成: 完成任务(条件：存在截止时间)
    进行中 --> 草稿: 重置(条件：无进行中子任务)
    已完成 --> [*]
```

| 状态 | 触发事件 | 转移条件 |
| ---- | -------- | -------- |
| 草稿 → 进行中 | 开始任务 | 标题完整 |
| 进行中 → 已完成 | 完成任务 | 记录完成时间 |
| 进行中 → 草稿 | 重置 | 无子任务进行中 |

## 八、与 requirements 的追溯关系（强制）

- 每个模块、每条关键流程、每个状态机都标注**来源需求编号**（FR-x / 业务规则 x）。
- 目标：任何一处设计都能追溯到需求，任何需求都有对应设计承接；无对应需求的设计要标注并确认（可能是蔓延，需警惕）。

```
| 设计物 | 内容 | 追溯需求 |
| 删除任务流程 | ... | BR-3(仅创建者可删) |
```

## 九、建议增强

### 用户故事格式（可选模板）
```
作为 <角色>，我希望 <功能>，以便 <价值>。
示例：作为 成员，我希望按状态筛选任务，以便快速找到待办。
```

### 关键交互的步骤序列（含确认、撤销、补偿）
对高风险/不可逆操作，写出步骤序列，覆盖：
- **确认**：操作前确认（二次确认对话框）。
- **撤销**：操作可取消/回退的方式。
- **补偿**：级联操作失败时的补偿（部分成功回滚）。
```
删除任务步骤：用户点删除 → 弹确认框 → 确认 → 删除 → 提示成功（可撤销：提供 5 秒 undo）。
补偿：删除时若存在关联子任务，先提示影响范围；取消则不做任何修改。
```

### 多端差异说明（若适用）
- 若 Web / 移动 / 平板行为不同，说明差异点（布局、交互、能力）。
```
移动端：列表走卡片式；Web：表格式；删除在移动端走长按菜单。
```

### 无障碍与基础可用性检查点
- **对比度**：正文文字与背景对比度 ≥ 4.5:1。
- **焦点**：所有可交互元素键盘可达、焦点可见。
- **文案**：按钮/错误提示使用明确动词与清晰描述；错误提示说明原因与下一步。
- 关键操作提供语义化标签与 ARIA（按需）。

## 十、异常与边界流程

- 对主流程补充异常与边界路径：失败、取消、超时、非法输入、依赖不可用。
- 至少写出一条**完整异常流**（判定条件、处理动作、呈现、恢复方式）。

## 十一、输出

ALWAYS 使用以下结构生成产品方案：

```
# 产品设计方案
## 0. 追溯总览（模块/流程 ↔ 需求编号 映射）
## 1. 功能模块图（含 Mermaid）
## 2. 信息架构与页面清单
## 3. 导航结构
## 4. 关键用户流程（含分支，Mermaid）
## 5. 业务流程与状态机（状态/事件/转移条件）
## 6. 关键交互步骤序列（含确认/撤销/补偿）
## 7. 异常与边界流程（≥1 条完整）
## 8. 各核心页面的五态定义
## 9. 角色 × 功能权限矩阵
## 10. 多端差异（如适用）
## 11. 无障碍与可用性检查点
## 12. 待确认问题
```

## 十二、质量门槛

### 完成判定（全部满足才可进入下一阶段）

- [ ] 主流程完整（明确起止、判断、分支）
- [ ] 至少一条**异常/边界流完整**
- [ ] **权限矩阵无空白关键角色**（每个关键角色都有明确权限结论）
- [ ] 所有核心页面补齐**五态**
- [ ] 关键业务实体有**状态机**描述（状态/事件/转移条件）
- [ ] 设计物与需求编号**可追溯**，无悬空需求
- [ ] 未关闭的分类判定：是否存在指向需求阶段的未关闭问题（若有则回退）

### 不合格信号

- 只有 happy path，无分支/异常流
- 页面未覆盖五态
- 权限矩阵缺关键角色或格子空白
- 业务流转仅一句描述，无状态机
- 设计无法追溯到需求编号
- 直接照抄架构/技术方案而非产品视角

## 十三、完整示例：含 Mermaid 流程的产品方案（精简）

```
# 产品设计方案（示例：简化版任务管理 Web 应用）

## 0. 追溯总览
- 登录流程 → FR-1
- 任务状态机 → BR-2（状态流转规则）

## 1. 功能模块图
graph TD
    Auth[认证模块] --> Core[任务核心]
    Core --> B[看板模块]

## 2. 信息架构
├── 登录页
└── 主框架
    ├── 任务列表页
    ├── 看板页
    └── 设置页

## 4. 关键用户流程（含分支）
flowchart TD
    A[进入首页] --> B{已登录?}
    B -- 否 --> C[登录页]
    C --> D{凭证正确?}
    D -- 否 --> E[错误提示]
    E --> C
    D -- 是 --> F[任务列表]
    B -- 是 --> F
    F --> G{点击新建?}
    G -- 是 --> H[创建任务]
    H --> F

## 5. 业务流程与状态机
stateDiagram-v2
    [*] --> 草稿
    草稿 --> 进行中: 开始(标题完整)
    进行中 --> 已完成: 完成(记录时间)
    进行中 --> 草稿: 重置(无子任务)

## 8. 核心页面五态（节选：任务列表）
- 正常：表格 + 状态筛选
- 加载：骨架屏
- 空：空状态引导创建
- 错误：失败 + 重试
- 无权限：提示 + 返回

## 9. 权限矩阵
功能\角色 | 成员 | 管理员
登录      | √    | √
创建任务  | √    | √
删除任务  | 仅自己 | 全部
管理成员  | –    | √

## 12. 待确认问题
- [关闭] 是否支持看板拖拽？→ 用户确认：本期仅视图，不做拖拽。
```

## 常识

- 产品设计是连接"需求"与"实现"的桥梁：越清晰，后续架构、UI、开发、测试越省力。
- 先确认主流程，再覆盖异常与边界，避免本末倒置。
- 设计要追溯到需求，既保证需求不被遗漏，也防止范围蔓延。
