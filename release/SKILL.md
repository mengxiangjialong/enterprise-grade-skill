# release

负责项目**最终发布**。

## 最终目标

> 项目是否可以正式上线——以门禁全绿 + 冒烟通过 + 监控无异常 + 回滚可用为准。

## 一、发布门禁清单（写死，逐项为闸门）

严格按顺序执行，每道闸门通过才进下一道：

```
代码检查    → lint/格式/依赖检查通过
测试        → 相关测试通过（testing 阶段结论为通过）
安全        → security-review 无未处理 Critical/High
构建        → 产物确定、可复现、版本可追溯
部署        → 按策略部署成功
健康检查    → 服务就绪 + 依赖可用
Smoke Test  → 核心主流程冒烟通过
监控        → 发布后关键指标无异常
```

任何闸门不通过即**中止发布**。

## 二、带病发布禁止规则（强制，与 security/testing 绑定）

- **禁止带病发布**：当 security-review 或 testing 结论为"未通过/未通过门禁"时，**不得进入 release**。
- 与 `security-review`（Critical/High 未清零禁止 release）和 `testing`（失败项未处理）结论绑定。
- 存在未清零的安全高危、未处理的失败用例、code-review 未清 Critical/Major → 一律禁止发布。
- 不做"先上线再补"式的带病发布。

## 三、前置检查项（全部可勾选）

发布前逐项勾选，缺一项即为未通过：

- [ ] **环境变量**：目标环境密钥与配置齐备，无硬编码
- [ ] **数据库迁移**：迁移脚本就绪、可回滚、数据检查通过
- [ ] **配置文件**：与目标环境匹配，无残留开发配置
- [ ] **镜像/构建**：镜像正确、版本标签可追溯
- [ ] **CI/CD**：流水线全绿
- [ ] **日志**：正常运行可正确产出，无敏感信息泄漏
- [ ] **监控**：可用性/错误/资源有监控与告警
- [ ] **回滚**：回滚方案明确可用

## 四、回滚方案（强制）

发布前必须给出可执行的回滚方案，包含：

- **触发条件**：什么情况下触发回滚（如错误率超阈值、健康检查失败、冒烟失败、崩溃）。
- **回滚步骤**：具体步骤顺序（切回上一版本镜像/代码、恢复数据、执行回滚迁移）。
- **数据兼容说明**：本次迁移/数据变更是否可逆；回滚时数据处理方式（回滚迁移/数据保留/兼容性），确保回滚不破坏数据。

```
回滚方案：
- 触发条件：发布后 15min 内错误率 > 5% 或 健康检查失败。
- 步骤：① 切回上一构建镜像 <image:v_prev>；② 执行 db/migration 回滚脚本 down；③ 重启并验证健康。
- 数据兼容：本次为兼容迁移（加列有默认值），回滚仅移除新增列，不丢存量数据。
```

## 五、发布报告必须含（强制）

- **版本号**：发布版本/构建号。
- **变更范围**：本次改动内容（功能/修复/兼容性）。
- **证据链接或记录**：每道闸门的证据（CI 链接、测试报告、安全结论、构建产物、冒烟输出、监控快照）或其记录。
- 缺任一即报告不完整。

## 六、建议增强

### 发布策略选择（适用条件）
- **滚动（Rolling）**：适合无状态、多副本服务；平滑替换，停机短；发布中混合版本需兼容。
- **蓝绿（Blue/Green）**：适合可整体切换、需快速回滚；成本高（双环境）、数据兼容要求高。
- **金丝雀（Canary）**：适合高流量或变更风险大；按比例放量与观察，稳但发布周期长。
- 选择依据：有状态性、停机/回滚容忍度、规模与风险。

### 发布后观察窗口与成功判定指标
- 明确**观察窗口**（如 15–30 分钟）与**成功判定指标**：
  - 可用性：健康检查持续 OK
  - 错误率：低于阈值（如 5xx < 0.5%）
  - 延迟/资源：P95 延迟、CPU/内存正常
  - 关键业务：冒烟功能回调正常
- 观察期后指标正常方确认发布成功；异常则触发回滚。

### 数据库迁移与发布的顺序约束
- 遵循**兼容顺序**：先应用可向前兼容的迁移（加列/加表、设默认值），再发布新代码；保证老版本可与新 schema 共存。
- **破坏性迁移**（删表/改列）不得先于代码兼容处理；回滚迁移顺序与逻辑保持一致。
- 明确记录迁移顺序：`迁移 A → 发布 → 后期清理`。

### 密钥与配置在目标环境的核对步骤
- 发布时核对目标环境：所需环境变量/密钥**齐全**且与目标环境匹配，非本地/开发值。
- 核对方式：与配置清单逐项比对；确认密钥来源（环境变量/密钥服务），仓库无明文。
- 记录核对结果。

## 七、输出

ALWAYS 使用以下结构生成发布报告：

```
# 发布报告
## 版本信息（版本号/构建号/变更范围）
## 发布门禁清单结果（代码/测试/安全/构建/部署/健康/冒烟/监控 + 证据）
## 前置检查项勾选结果（环境变量/迁移/配置/镜像/CI/日志/监控/回滚）
## 发布策略与部署过程
## 数据库迁移顺序与数据兼容说明
## 健康检查与 Smoke Test 结果
## 发布后观察窗口与监控指标
## 回滚方案（触发条件/步骤/数据兼容）
## 结论：是否可视为正式上线
```

## 八、质量门槛

### 完成判定（全部满足）

- [ ] **门禁全绿**：代码/测试/安全/构建/部署/健康/冒烟/监控均通过（证据链）
- [ ] **冒烟通过**：核心主流程验证成功
- [ ] **监控无异常**：观察窗口内指标正常
- [ ] **回滚方案可用**：触发条件/步骤/数据兼容明确
- [ ] 报告含**版本号、变更范围、证据**
- [ ] 无带病发布（security/testing/code-review 结论均通过）

### 不合格信号

- 某门禁未过却继续发布/宣布上线
- 存在未处理的 security 高危 / testing 失败 / code-review 未清项却发布
- 无回滚方案或回滚不完整（无触发条件/数据兼容）
- 报告缺版本号、变更范围或证据
- 前置检查项未逐项可勾选核查

## 九、发布报告示例（精简）


## 常识

- 发布是高风险动作：每道闸门都要有真实证据，阻断项绝不带病发布。
- 有清晰的回滚方案，出问题时可快速恢复，比追求零失误更稳妥。
- 门禁全绿 + 回滚可用，缺一不可。
