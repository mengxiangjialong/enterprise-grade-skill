# release

负责项目**最终发布**。

## 最终目标

> 项目是否可以正式上线。

## 标准流程

严格按顺序执行：

```
代码检查
  ↓
测试
  ↓
安全检查
  ↓
构建
  ↓
部署
  ↓
健康检查
  ↓
Smoke Test
  ↓
发布
  ↓
监控
```

## 发布前检查项

- **环境变量**：密钥与配置齐备，不硬编码
- **数据库迁移**：迁移脚本就绪、可回滚、数据检查
- **配置文件**：与目标环境匹配
- **Docker**：镜像构建正确、版本可追溯
- **CI/CD**：流水线通过
- **日志**：正常运行可产出正确日志，无敏感信息泄漏
- **监控**：关键指标（可用性、错误率、资源）有监控与告警
- **回滚方案**：具备明确的回滚路径与触发条件

## 各环节要则

- **代码检查 / 测试 / 安全检查**：确保前面阶段结论为"通过"，阻断项未清零不发布。
- **构建**：产物确定、可复现、版本号清晰。
- **部署**：按发布策略（蓝绿/滚动/金丝雀）执行，做好备份。
- **健康检查**：服务就绪性、依赖可用性验证。
- **Smoke Test**：核心业务主流程冒烟通过。
- **监控**：发布后观察错误率与关键指标，平稳后确认。

## 输出

ALWAYS 使用以下结构生成发布报告：

```
# 发布报告
## 版本信息（版本号、构建号、变更内容）
## 前置检查结果（代码/测试/安全/Docker/CI、环境变量/迁移/配置/日志/监控/回滚）
## 构建与部署过程
## 健康检查结果
## Smoke Test 结果
## 发布确认与监控状态
## 风险与回滚说明
## 结论：是否可以视为正式上线
```

## 常识

- 发布是高风险动作：每道闸门都要有真实证据，阻断项绝不带病发布。
- 有清晰的回滚方案，出问题时可快速恢复，比追求零失误更稳妥。
