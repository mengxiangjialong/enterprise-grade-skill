# requirements-analysis

将用户的自然语言需求转换成**明确、可执行**的开发需求。

## 最终目标

> 明确系统需要做什么，且每一处关键结论都来自用户确认而非假设。

## 一、核心原则与强制检查点

> **本阶段必须先向用户提问以确认需求。**

初始需求往往模糊、不完整、有歧义，只有通过提问逐项澄清，才能得到可靠的需求规格。

两条**强制检查点**，缺一不可：

1. **未提问确认，不得产出最终规格**——直接在没有任何提问确认的情况下输出"需求规格说明"，视为本阶段不合格，必须回头先提问。
2. **有待确认问题（未关闭项），不得标记阶段完成**——规格中存在未关闭的待确认问题，则本阶段不能判定为完成，必须继续向用户澄清直至关闭。

### 强制性要求

- **先问后写**：动手整理需求规格前，必须先向用户提出确认性问题。
- **逐项确认**：对不确定的关键维度逐项提问，不擅自替用户做决定。
- **确认后才可产出**：得到用户对问题清单的回答后，才生成最终需求规格。
- **闭环复述**：形成规格后，向用户复述关键结论，请其确认无误。
- **未关闭项阻塞完成**：存在未关闭的待确认问题，阶段状态不得为 `done`（应回到 `in-progress` 继续澄清）。

## 二、提问流程

### 第 1 步：判定项目类型

先判断需求属于哪种项目类型，再选用对应的提问清单：

| 类型 | 典型特征 | 关注重点 |
| ---- | -------- | -------- |
| **Web** | 浏览器访问，前后端，多页面 | 并发/登录态、浏览器兼容、接口、部署环境 |
| **移动** | iOS/Android 或跨端 | 系统版本、推送、离线、权限申请、应用市场 |
| **CLI** | 命令行工具 | 命令/参数、输出格式、退出码、脚本化调用 |
| **内部工具** | 公司内部使用 | 数据权限、审计、集成现有系统、用户数/规模 |
| **数据管道** | 批/流式处理数据 | 数据源/目标、调度、吞吐量、容错重试、数据量 |

### 第 2 步：向用户提问（核心动作）

围绕下列维度提问。**通用方向 + 按类型的专属问题**：

**通用问题（所有类型必问）：**
- 用户是谁？目标/使用者角色有哪些？
- 要解决什么问题？核心痛点和期望的业务价值？
- 核心功能有哪些？哪些是 MVP（Must），哪些可延后？
- 使用场景是什么？在什么时间、地点、情况下使用？
- 输入是什么（数据来源与形式）？输出是什么（结果/文件/通知）？
- 有哪些必须遵循的业务规则与约束？
- 异常情况如何处理（非法输入、失败流程、依赖不可用）？
- 权限要求是什么？谁能做什么？
- 验收标准是什么？怎样才算"做完"？
- 范围边界？明确"做什么"与"不做什么"？

**按类型的专属问题：**

- **Web**：需要适配哪些浏览器/分辨率？并发用户数量级？是否需要登录/角色权限？部署环境（内网/公网）？
- **移动**：目标平台与最低系统版本？是否需要离线功能/推送？有哪些系统权限（相机/定位/通知）？
- **CLI**：是否需脚本化/自动化调用？参数解析与帮助信息？异常时的退出码与错误输出？
- **内部工具**：用户规模多大？是否需要对接现有系统（SSO/LDAP/内部 API）？数据敏感级别与审计要求？
- **数据管道**：数据源与目标是什么？数据量级与增长？调度频率？失败重试与完整性要求？

提问技巧：
- **开放式 + 封闭式结合**：先开放了解全貌，再封闭（二选一/确认）钉死细节。
- **给出选项降低负担**：对难答问题提供几个合理候选让用户选。
- **MVP 优先**：必答项先问，疑似可延后的次之。

### 第 3 步：整理、复述并闭环

- 汇总用户回答，形成需求规格。
- 向用户**复述关键结论**（目标、范围、核心功能、验收标准），请求最终确认。
- 仍有疑问的条目列入"待确认问题"，**明确请用户补充**；在用户回答前，该问题保持"未关闭"。

## 三、用户画像 / 角色简表模板

输出一个简洁角色简表，帮助后续设计与权限设计：

```
# 用户角色简表
| 角色 | 描述 | 核心目标 | 关键权限 | 使用频率 |
| ---- | ---- | -------- | -------- | -------- |
| 管理员 | ... | ... | ... | ... |
| 普通用户 | ... | ... | ... | ... |
```

## 四、优先级标注

为每项功能/需求标注优先级，便于排期与砍范围：

- **Must**：必须有的核心功能（MVP，未实现则产品不成立）
- **Should**：重要、应尽量实现
- **Could**：锦上添花，有余力再做
- **Won't**：明确本期不做（记录以防误解）

在功能需求表中以 `优先级` 字段标注。

## 五、功能需求必须三要素

> 每条功能需求**强制**包含：编号 + 描述 + 验收标准（可测）。

```
| 编号 | 功能描述 | 优先级 | 验收标准（可测试） |
| ---- | -------- | ------ | ------------------ |
| FR-1  | 用户可以登录 | Must | 输入正确账号密码可进入首页；错误密码返回明确错误提示 |
```

- 描述要具体，去掉"大概/尽量"。
- 验收标准必须是**可测断言**（"（当……时）系统应……"），让 tester / 开发能据此验证。

## 六、范围与 Out of Scope

明确写出 **Out of Scope**，防止范围蔓延：

- **In Scope**：本期明确交付的功能清单。
- **Out of Scope**：明确不做的内容，写明理由，防止后续"加一点"。
- **边界约定**：系统边界（如不负责支付、不负责数据迁移等）。

Out of Scope 写法示例：
```
## 4. 范围
In Scope：用户注册登录、任务创建/编辑/查询、基础看板。
Out of Scope：消息通知、移动端、多语言、支付（无支付场景，先不做）；
            数据迁移一次性脚本由运维另行处理。
```

## 七、非功能需求量化模板

非功能需求要**可量化、可验收**，不要写抽象词，按以下类别给出具体指标：

```
# 非功能需求
## 性能
- API 平均响应时间：P95 目标 ≤ 800ms
- 并发：支持 ≥ 500 并发请求不失效
- 页面首屏加载：≤ 2.5s（4G 网络）
## 可用性
- 目标可用性：≥ 99.5%（月度）
- 容错：单点依赖可用降级，缓存故障不影响核心读取
## 安全级别
- 认证方式：JWT + 刷新令牌
- 密码哈希：bcrypt/argon2
- 数据传输：全站 HTTPS
## 兼容范围
- 浏览器：Chrome/Edge/Firefox 最近两个主版本
- 移动端：Android 9+，iOS 13+
## 数据
- 数据量级预估与增长预期
- 备份与留存策略
```

## 八、合规与隐私提问

涉及用户数据时必问，并记录到规格中：

- 数据敏感级别（公开/内部/机密/个人数据）
- 数据留存与删除策略（留存多久、如何删除）
- 是否涉及个人隐私数据（姓名、手机、设备等）及授权范围
- 是否需要符合某法规/内部合规（如 GDPR、个人信息保护法等）
- 数据是否可跨境/第三方共享

## 九、需求变更记录区

需求可能演进而非一次定型。在规格中保留变更区：

```
# 变更记录
| 版本 | 日期 | 变更内容 | 变更原因 | 影响范围 |
| ---- | ---- | -------- | -------- | -------- |
| v1.0 | ...  | 初始版   | -        | -        |
| v1.1 | ...  | 增加 X   | 用户反馈 | FR-x, 模块Y |
```

## 十、待确认问题闭环

- 全部存疑项列入"待确认问题"，每条标注：关联维度 + 具体疑问 + 状态（开放/已关闭）。
- **未关闭项不得标记阶段完成**：只有全部关键待确认问题关闭，才可将本阶段置为 `done`。
- 用户回答后立即更新状态并同步进正文，不遗留悬空项。

## 十一、输出

先完成提问确认并**关闭全部关键待确认问题**，再 ALWAYS 使用以下结构生成需求规格说明：

```
# 需求规格说明
## 0. 需求确认记录（已提问并确认的内容）
## 1. 项目概述
## 2. 目标用户与角色简表
## 3. 业务目标与价值
## 4. 范围（In Scope / Out of Scope / 边界约定）
## 5. 功能需求（编号 + 描述 + 优先级 + 验收标准）
## 6. 业务规则
## 7. 异常与边界情况
## 8. 权限需求
## 9. 非功能需求（量化指标）
## 10. 合规与隐私
## 11. 验收标准汇总
## 12. 待确认问题（含状态，须全部关闭后方可完成）
## 13. 变更记录
```

## 十二、质量门槛

### 合格需求规格的判定（全部满足）

- [ ] 核心维度均有**用户的确认记录**（谁、问题、核心功能、范围、验收标准等）
- [ ] 每条功能需求含**编号 + 描述 + 可测验收标准**
- [ ] 优先级已标注（Must/Should/Could）
- [ ] 明确写出 **Out of Scope**
- [ ] 非功能需求给出**量化指标**
- [ ] **无未关闭的阻断性待确认问题**
- [ ] 用户已对关键结论**复述确认**

### 不合格信号（出现即需返工）

- 出现模糊词："大概/尽量/等/合适/较好"
- 功能只有描述、**没有验收标准**
- 没有写 **Out of Scope**
- 非功能需求全是抽象词、无量化指标
- 关键维度**没有用户确认记录**（全靠假设）
- 存在**未关闭的待确认问题**却声明"已完成"

## 十三、完整示例：合格需求规格（精简演示）

```
# 需求规格说明（示例：简化版任务管理 Web 应用）
## 0. 需求确认记录
- 日期 2026-03-01，已向用户确认：角色=个人/团队；核心=任务增删改查；仅 Web；首期不要消息通知。

## 2. 目标用户与角色简表
| 角色 | 描述 | 核心目标 | 关键权限 | 使用频率 |
| 成员 | 创建和完成任务 | 记录待办 | 操作自己的任务 | 每日 |
| 管理员 | 管理成员 | 维护团队 | 管理所有任务与成员 | 每周 |

## 4. 范围
In Scope：用户登录、任务 CRUD、任务状态流转、按状态筛选。
Out of Scope：消息通知、移动端、多语言、支付。

## 5. 功能需求
| 编号 | 描述 | 优先级 | 验收标准 |
| FR-1 | 用户登录 | Must | 正确账号密码可进入首页；错误密码返回"用户名或密码错误" |
| FR-2 | 创建任务 | Must | 提交标题+截止日期后任务出现于列表；标题为空时提示且不创建 |
| FR-3 | 列表按状态筛选 | Should | 点击"已完成"仅显示已完成任务 |

## 9. 非功能需求
性能：P95 接口响应 ≤ 800ms；并发 ≥ 200。
可用性：≥ 99%。
安全：HTTPS；密码 bcrypt。
兼容：Chrome/Edge/Firefox 最近两版。

## 12. 待确认问题
- [关闭] 是否需要消息通知？→ 用户确认：首期不做。
- （无未关闭项）
```

## 常识

- 需求是最上游，改动成本最高：宁可多问，也不要让错误扩散到整个流水线。
- 提问是对用户的尊重与保护：先确认方向，才能避免后续大量返工。
- 一份"合格"的规格 = 方向明确 + 可测 + 有确认记录 + 无悬空问题，缺一不可。
