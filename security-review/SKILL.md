# security-review

负责项目**安全检查**。

## 最终目标

> 项目是否存在明显安全风险。

## 检查维度

- **SQL Injection**：是否使用参数化查询/ORM，有无拼接 SQL
- **XSS**：用户输入是否被转义，存储/反射/ DOM 型
- **CSRF**：状态变更请求是否有防护
- **SSRF**：服务端请求外部 URL 是否有白名单/限制
- **权限绕过**：鉴权链路是否可被绕过
- **越权**：水平/垂直越权检查（IDOR 等）
- **敏感信息泄露**：凭据、密钥、Token 是否入代码/日志
- **密码安全**：是否使用安全的哈希与存储策略
- **Token 安全**：签发、过期、泄漏处理
- **Session 安全**：cookie 属性、固定/劫持
- **文件上传**：类型/大小/路径校验，防任意文件上传
- **命令执行**：是否将用户输入传入系统命令
- **API 限流**：是否防暴力与滥用
- **日志脱敏**：日志是否夹杂敏感数据
- **第三方依赖漏洞**：依赖是否存在已知 CVE

## 审查原则

- **默认不安全**：对鉴权、输入、输出做最坏假设。
- **纵深防御**：不止依赖单点防护。
- **最低权限**：权限与运行时权限遵循最小化。

## 风险分级

```
Critical  可直接被利用的高危漏洞，必须修复后才能上线
Major     较易利用，造成较大影响，应修复
Minor     影响有限的隐患，建议修复
```

## 输出

ALWAYS 使用以下结构生成安全检查报告：

```
# 安全检查报告
## 1. 检查范围与目标
## 2. 逐项检查结果（维度、结论、证据）
## 3. 高危风险清单（位置、威胁、利用方式、修复建议、分级）
## 4. 中低风险清单
## 5. 依赖漏洞列表
## 6. 结论：是否存在明显安全风险，是否可以继续上线流程
```

## 常识

- 安全问题上线后代价极高：review 阶段务必把关。
- 发现漏洞及时反馈修复，高危项未清零前不应进入 release。
