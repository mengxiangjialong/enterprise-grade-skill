# security-review

负责项目**安全检查**。

## 最终目标

> 明确项目是否存在明显安全风险，并给出可执行、可验证的修复与门禁结论。

## 一、必查项（写死）

- **鉴权**：所有受保护接口/资源是否都有认证与授权校验，链路可否绕过。
- **越权（水平/垂直）**：水平（操作他人资源）、垂直（低权限访问高权限功能），含 IDOR。
- 这两类**必须审查**，缺查即不合格。

## 二、检查维度 + 每项"如何验证"（强制）

每项给出可执行的验证方法：

- **SQL Injection**
  验证：搜索是否用参数化/ORM（无字符串拼接 SQL）；尝试注入 payload 观察是否被拦截。
- **XSS**
  验证：用户输入是否统一转义；存储/反射/DOM 型分别用 payload 测试输出位置。
- **CSRF**
  验证：状态变更请求是否校验来源（token/同源）；无则测试伪造请求。
- **SSRF**
  验证：服务端请求外部 URL 是否有域名/IP 白名单或协议限制；测试内部地址访问。
- **权限绕过 / 鉴权**
  验证：逐个受保护 endpoint 不带/篡改凭证访问；确认中间件/注解覆盖全链路。
- **越权（水平/垂直）**
  验证：用用户 B 改 A 的资源 ID；用低权限调高权限接口。
- **敏感信息泄露**
  验证：全库搜索密钥/Token/密码是否入库、入配置、入日志；见第四节。
- **密码安全**
  验证：密码是否用 bcrypt/argon2 等慢哈希，非明文/弱哈希。
- **Token 安全**
  验证：签发、过期、JWT 签名校验、刷新与吊销、是否可被解码篡改。
- **Session 安全**
  验证：cookie 是否 HttpOnly/Secure/SameSite；有无固定会话/劫持。
- **文件上传**
  验证：类型/大小/内容校验、路径穿越、是否可上传可执行文件（专项见七节）。
- **命令执行**
  验证：用户输入是否进入系统命令；是否参数化、有白名单（专项见七节）。
- **API 限流**
  验证：登录/关键接口是否限流，防暴力；返回 429 与 Retry-After。
- **日志脱敏**
  验证：日志是否输出密码/Token/手机号等；错误回显是否泄漏栈与配置（见第四节）。
- **第三方依赖漏洞**
  验证：锁文件、跑 CVE 扫描（见第三节）。

## 三、依赖与供应链（强制）

- **锁文件**：项目使用 lock file（package-lock / go.sum / pom 锁版本等）固定依赖版本，可复现。
- **已知 CVE**：对锁定版本跑漏洞扫描（如 npm audit、grype、trivy 等），列出有 CVE 的依赖与版本。
- **密钥是否入库**：全库排查 `.env`、密钥文件、硬编码凭据是否被提交进仓库；用加密扫描/内容搜索确认。
- 供应链：外部依赖来源可信、版本固定、最小化引入。

## 四、敏感信息全覆盖（代码/配置/日志/错误回显）

敏感信息在四处都要排查：

- **代码**：硬编码密码/密钥/Token、生产地址、测试真实账号。
- **配置**：仓库内明文密钥、`.env` 是否入仓库、密钥是否走密钥服务/环境变量。
- **日志**：是否记录密码、Token、手机号、身份证、支付信息。
- **错误回显**：前端/API 是否把堆栈、SQL、依赖版本、敏感配置回显给客户端。

对每处给出"是否脱敏/外置/移除"的结论。

## 五、风险分级 + 发布门禁绑定（强制）

```
Critical  可直接被利用的高危漏洞（鉴权缺失/越权/注入等），必须修复
High      较易利用、影响较大，必须处理
Medium    中等影响，应在发布前处理或登记补偿
Low       影响有限，记录即可
```

### 发布门禁（写死）
> **Critical / 高危（High）项未清零 → 禁止 release。**

- 存在 Critical / High → 本阶段判定为"存在明显安全风险，未通过"，回退修复；未清零不得 release。
- Medium 若无法立即修，须有**明确豁免 + 补偿控制**记录（接受风险的理由 + 缓解措施 + 跟进）。
- 全部清零或获豁免 → 可继续进入 release 流程。

## 六、基础 OWASP 映射（便于对照）

| 检查项 | 对应 OWASP Top 10 (2021) |
| ------ | ------------------------ |
| 鉴权/会话 | A01 失效的访问控制、A07 身份认证失败 |
| SQLi/XSS/命令执行 | A03 注入 |
| 敏感信息 | A02 加密失败、A05 安全配置错误、A09 日志中暴露敏感 |
| 文件上传/SSRF | A03 注入、A10 服务端请求伪造 |
| 依赖漏洞 | A06 漏洞与过时组件 |

## 七、专项检查步骤（文件上传 / SSRF / 命令注入）

### 文件上传
1. 校验扩展名 + MIME 类型（双重，防伪装）。
2. 校验内容/大小上限；重命名存储，不使用用户提供的路径。
3. 存储位置不可执行，访问走 CDN/静态隔离，防路径穿越。
4. 测试：上传可执行脚本/恶意文件名/shell 文件名，确认被拒且不落执行目录。

### SSRF
1. 定位所有服务端发起的 URL 请求。
2. 强制域名/IP 白名单或协议+端口限制。
3. 测试：请求 `169.254.169.254`（云元数据）、内网 IP、`file://` 等，确认被拦。

### 命令注入
1. 排查用户输入是否拼入 shell 命令。
2. 用参数化执行、命令白名单，禁止拼接。
3. 测试：注入 `; rm -rf` / `$(...)` / 反引号 payload，确认不安全。

## 八、安全修复后的回归验证（强制）

- 每个高危修复后，必须**复测该漏洞**（跑原利用 payload/场景）确认不再可被利用。
- 同时回归相关功能（修复未破坏原有行为）。
- 在报告记录：`修复项 ↔ 复测结果 ↔ 回归结果`。

## 九、合规相关最小检查（若需求已声明）

- 仅当 requirements 阶段已声明合规要求（如 GDPR / 个保法 / 行业合规）时执行最小检查。
- 覆盖：数据收集最小化、用户授权/同意、留存与删除、跨境传输、导出匿名化。
- 未声明合规要求则注明"本项目未声明特定合规需求，将按通用安全要求执行"。

## 十、输出

ALWAYS 使用以下结构生成安全检查报告：

```
# 安全检查报告
## 1. 检查范围与目标
## 2. 必查项结果（鉴权、水平/垂直越权）
## 3. 逐项检查结果（维度、如何验证、结论、证据）
## 4. 依赖与供应链（锁文件/CVE/密钥入库）
## 5. 敏感信息排查（代码/配置/日志/错误回显）
## 6. 高危/高风险清单（位置、威胁、利用方式、验证、修复建议、分级）
## 7. 中低风险清单
## 8. 豁免与补偿控制记录（如有）
## 9. 专项检查（文件上传/SSRF/命令注入，如适用）
## 10. 合规最小检查（如已声明）
## 11. 结论：是否明显安全风险；Critical/High 是否清零；是否允许 release
```

## 十一、质量门槛

### 完成判定（满足其一才可 release）

- [ ] **高危清零**：无未处理 Critical/High
- [ ] 或**有明确豁免 + 补偿控制记录**（理由 + 缓解 + 跟进）
- [ ] 鉴权、水平/垂直越权已必查并有结论
- [ ] 每个维度有**执行过的验证方法**记录
- [ ] 依赖（CVE、密钥入库）已检查
- [ ] 敏感信息四处（代码/配置/日志/错误回显）已排查
- [ ] 安全修复有**回归/复测**记录

### 不合格信号

- 存在 Critical/High 却仍判"允许上线"
- 未查鉴权/越权
- 维度缺验证方法，仅写"未发现"
- 未跑依赖 CVE / 未查密钥入库
- 敏感信息只查代码、漏日志/错误回显

## 十二、安全报告示例（精简）

```
# 安全检查报告（示例：任务服务）

## 1. 范围
Task API + 前端 + 依赖，对照 OWASP Top 10。

## 2. 必查项
- 鉴权：所有端点除 login 外均需 Bearer Token（已确认）。
- 水平越权：删除任务未校验归属 → 发现问题（见 §6 High-1）。

## 3. 逐项（节选）
| 维度 | 验证 | 结论 |
| SQLi | 全部参数化 | 通过 |
| XSS | 前端统一转义 | 通过 |
| ... | ... | ... |

## 4. 依赖
package-lock 已固定；`npm audit` 发现 2 个 High（lodash→CVE-2024-xxx）→ 见 High-2。

## 5. 敏感信息
- 代码/配置：无硬编码凭据（仓库排查通过）。
- 日志：登录日志含明文手机号 → 见 High-3。
- 错误回显：生产关闭堆栈（已确认）。

## 6. 高风险清单
| 级别 | 位置 | 威胁/利用 | 修复建议 |
| High-1 | TaskController.java:35 | 水平越权，任意用户删他人任务 | Service 校验归属 |
| High-2 | dependencies | lodash CVE 可被利用 | 升级 + 复扫 |
| High-3 | log config | 明文手机号入日志 | 脱敏手机号 |

## 7. 中低风险
- Medium：登录接口未限流 → 建议加限流（发布前处理或豁免）。

## 8. 豁免
- 登录限流 Medium 暂缓：补偿=部署层加网关限流，跟进=1 周内加应用层限流。

## 10. 合规
需求未声明特定合规需求。

## 11. 结论
存在 3 项高危未清零 → **存在明显安全风险，未通过；禁止 release**，移交修复后复测。
```

## 常识

- 安全问题上线后代价极高：review 阶段务必把关。
- Critical/高危未清零一律禁止 release，是写死的门禁。
- 每个"未发现"都应能从验证方法上站得住脚，而不是拍脑袋。
