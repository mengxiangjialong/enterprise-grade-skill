# testing

负责**测试**，验证系统功能是否符合需求。

## 最终目标

> 验证系统功能是否正确，达到可进入下一阶段的条件。

## 测试类型

- **Unit Test**：方法/函数的单元级验证
- **Integration Test**：模块间协作，含数据库、中间件
- **API Test**：接口契约与响应正确性
- **E2E Test**：端到端业务流
- **Regression Test**：变更后是否引入回归

## 用例生成

根据需求自动生成测试场景，覆盖：

```
正常情况      主流程的预期行为
异常情况      失败与异常路径
边界情况      极限值、临界条件
空数据        无数据时的行为
非法参数      参数校验与错误响应
权限          不同角色的访问控制
并发          并发写入/读取的正确性
网络异常      依赖不可用/超时下的处理
```

## 核心原则

> 测试的是需求，而不是单纯测试代码。

每条测试用例都应能追溯到一条需求/业务规则。

## 测试设计

- 以需求规格与业务规则为输入推导用例，而非只按实现写。
- 每条用例包含：编号、关联需求、前置条件、步骤、预期结果。
- 覆盖成功路径与失败/边界路径。
- 对鉴权、金额、并发等高风险逻辑重点覆盖。

## 执行与记录

- 运行测试并真实记录通过/失败结果与输出。
- 失败用例：记录失败点与报错，作为 debugging 的输入。

## 输出

ALWAYS 使用以下结构生成测试报告：

```
# 测试报告
## 1. 测试范围与策略
## 2. 用例清单（编号/关联需求/类型/前置/步骤/预期）
## 3. 执行结果汇总（通过/失败/跳过，通过率）
## 4. 失败用例明细（失败点、报错、复现）
## 5. 覆盖说明（各需求/边界的覆盖情况）
## 6. 结论：是否通过，未通过项转 debugging
```

## 常识

- 测试围绕需求展开：需求变更时，相关用例要随之更新。
- 自动化测试便于回归，优先为关键路径编写可重复执行的测试。
