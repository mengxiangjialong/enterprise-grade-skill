# testing

负责**测试**，验证系统功能是否符合需求。

## 最终目标

> 验证系统功能是否正确，明确是否能推进到 debugging/上线，且结论可核查。

## 〇、执行边界与指令优先级

> **用户显式指令优先于本技能指南。** 用户要求与以下冲突时，按用户要求执行并说明差异。

- **输入**：需求规格（带编号）、code-review 通过的代码、api/database 契约。
- **步骤**：需求 → 用例（固定结构）→ 场景覆盖 → 真实执行 → 记录结果 → 失败交接 debugging。
- **输出**：可追溯的测试用例 + 真实执行报告 + debugging 交接清单。
- **不可臆测**：执行结果必须真实记录（通过/失败/跳过+证据），不臆造"估计通过"。
- **何时停止**：核心需求未覆盖或失败未登记时判定未通过。
- **支持文件**：用例模板/报告模板可放 assets/ 或 references/，从 SKILL.md 引用并注明何时使用。

## 一、强制原则落地

> 测试的是需求，而不是单纯测试代码。

- **用例必须可追溯到需求编号**：每条用例标注其验证的需求/业务规则编号（FR-x / BR-x）。
- 从需求规格与业务规则推导用例，而不是只按实现写。
- 反向可查：每项核心需求至少被一条用例覆盖。

## 二、场景覆盖清单（写死，不可缺类）

对需求推导用例时，**必须**覆盖以下场景种类：

```
正常情况      主流程的预期行为
异常情况      失败与异常路径
边界情况      极限值、临界条件（空、0、极值）
空数据        无数据时的行为
非法参数      参数校验与错误响应
权限          不同角色的访问控制 / 越权
并发          并发写入/读取的正确性
依赖失败      外部依赖不可用/超时下的处理
```

缺一类即视为覆盖不完整。

## 三、用例结构固定（强制字段）

每条用例 ALWAYS 使用固定结构：

```
|---
用例编号：TC-001
关联需求：FR-2（创建任务）
类型：正常/异常/边界/空数据/非法参数/权限/并发/依赖失败
前置条件：已登录，存在用户 A
步骤：
  1. 提交标题+截止日期
  2. 调用 POST /api/v1/tasks
预期结果：
  - 返回 201
  - 任务出现在用户 A 的列表
```

强制字段：**编号、关联需求、前置、步骤、预期**，缺一不可。

## 四、执行结果必须真实记录（强制）

- **真实执行**，不臆造结果；逐条记录：`通过 / 失败 / 跳过`。
- 每条结果附**证据**：
  - 通过：关键断言/输出片段
  - 失败：失败断言、报错堆栈、复现要点
  - 跳过：跳过原因（环境缺失/未实现/依赖等）
- 汇总通过率，但**不以通过率掩盖失败项**：失败项必须逐条列明。

```
TC-001 通过：assert 201, task in list（日志行 xxx）
TC-003 失败：期望 401 实得 200 → 鉴权未生效，报错：no auth check
TC-007 跳过：并发压测依赖测试环境，当前缺失
```

## 五、失败用例 → debugging 的交接格式（强制）

失败用例按以下固定格式登记，作为 debugging 的输入：

```
|- 失败用例交接
用例：TC-003
现象：期望 401，实际 200
复现步骤：未带 Token 调用 DELETE /api/v1/tasks/1
证据：接口返回 200；日志无鉴权拦截记录
怀疑点：Controller 未加鉴权注解 / 拦截器未生效
```
- 每条失败项：**用例、现象、复现步骤、证据、怀疑点**。
- 交接清单整体交付给 debugging，作为下一阶段输入。

## 六、建议增强

### 测试类型选择指引（何时用）
- **Unit**：单个函数/类逻辑，快、准，覆盖分支与边界优先。
- **Integration**：跨模块协作（Service+DB、消息），验证契约与数据一致性。
- **API**：对外接口契约（状态码、响应结构、错误码、权限），接近真实调用。
- **E2E**：跨系统完整业务流，验证端到端正确，速度慢、成本高，聚焦主路径。
- 建议：关键业务用 Unit 打底，读写/权限用 API，核心旅程用小范围 E2E；按风险与成本选择，不追求全层级全自动化。

### 回归范围定义（改动影响分析）
- 变更后先做**影响分析**：改了什么模块、接触哪些接口/表、影响哪些需求。
- 据此挑选回归用例：被改路径 + 相邻模块 + 历史高危区。
- 回归范围记录下来，作为变更是否引入问题的依据。

### 测试数据与环境隔离
- 测试数据与生产隔离，不使用/污染真实数据。
- 每套测试环境有独立数据种子，可重置；测试数据生成幂等。
- 涉及敏感字段的测试用脱敏/假数据，不落真实个人信息。

### 自动化优先（不强制全自动化）
- 优先对可重复、关键路径用例做自动化，便于回归。
- 不适合自动化的（复杂的 UI 视觉、人工判断）可保留手工并说明原因。
- 自动化是手段不是目标：以"是否覆盖关键需求"为准。

## 七、输出

ALWAYS 使用以下结构生成测试报告：

```
# 测试报告
## 1. 测试范围与策略（对象、类型选择）
## 2. 场景覆盖清单（确认八类已覆盖）
## 3. 用例清单（固定结构：编号/关联需求/前置/步骤/预期）
## 4. 执行结果汇总（通过/失败/跳过 + 通过率）
## 5. 失败用例明细（现象/复现/证据/怀疑点）
## 6. 回归范围与影响分析
## 7. 测试数据与环境隔离说明
## 8. 覆盖说明（核心需求 ↔ 用例 映射）
## 9. 结论：是否通过；失败项交接 debugging
## 10. debugging 交接清单（格式见五）
```

## 八、质量门槛

### 完成判定（全部满足）

- [ ] **核心需求有覆盖**：每项核心需求至少一条可追溯用例
- [ ] **八类场景均已覆盖**（正常/异常/边界/空/非法/权限/并发/依赖失败）
- [ ] 用例结构完整（编号/关联需求/前置/步骤/预期）
- [ ] **执行结果真实记录**（通过/失败/跳过 + 证据），无臆造
- [ ] **失败项已登记**且按格式交接 debugging
- [ ] **结论明确**是否可推进（通过 → 下一阶段；有失败 → 交接 debugging）

### 不合格信号

- 用例不关联需求编号
- 场景缺类（缺并发或依赖失败等）
- 用例缺前置/步骤/预期
- 结果为"估计通过"而非真实执行证据
- 有失败项却未交接 debugging，或结论含糊
- 测试数据/环境未隔离

## 九、含追溯关系的测试报告示例（精简）

```
# 测试报告（示例：任务服务）

## 1. 范围与策略
对象：TaskController/Service/Repository；类型选择：Service 用 Unit，读写/权限走 API 测试。

## 2. 场景覆盖
正常/异常/边界/空数据/非法参数/权限/并发/依赖失败 均已规划。

## 3. 用例清单（节选）
| 编号 | 关联需求 | 类型 | 前置 | 步骤 | 预期 |
| TC-001 | FR-2 | 正常 | 登录A | 创建任务 | 201 + 出现在列表 |
| TC-002 | FR-2 | 非法参数 | 登录A | 空标题提交 | 422 TITLE_EMPTY |
| TC-003 | BR-3 | 权限 | 登录B | A 删除 B 的任务 | 403 FORBIDDEN |
| TC-008 | FR-3 | 并发 | 登录A | 并发修改同一任务 | 不丢更新/明确冲突 |

## 4. 执行结果
总 8：通过 6 / 失败 1 / 跳过 1；通过率 75%。
- TC-001 通过（201 + 入列，日志 xxx）
- TC-003 失败：期望 403，实得 200（越权，见 §5）
- TC-008 跳过：并发环境缺失

## 5. 失败明细
|- 用例：TC-003
  现象：期望 403，实际 200
  复现：B 直接调 DELETE /api/v1/tasks/{A的任务}
  证据：返回 200；Service 未校验归属
  怀疑点：删除逻辑缺少 user_id 归属校验

## 6. 回归
改动为任务 CRUD，回归覆盖列表/删除/并发路径。

## 8. 覆盖
FR-2→TC-001/002；FR-3→TC-004..008；BR-3→TC-003。

## 9. 结论
未通过：存在 1 失败（越权）。交接 debugging，其余通过项可先行复验。

## 10. debugging 交接清单
[TC-003 交接格式如上]
```

## 常识

- 测试围绕需求展开：需求变更时，相关用例随之更新。
- 自动化便于回归，优先为关键路径编写可重复执行的测试。
- 测试报告的价值在于**真实与可追溯**，不在于通过率数字好看。
